# GraphNotes — канонический контекст Product Observer

## Статус документа

Этот файл — рабочий бриф Product Observer, не второе продуктовое ТЗ.
Его можно целиком передать новому чату или воркеру.

Документ описывает продуктовую ценность, роли, пользовательские сценарии и критерии соответствия замыслу. Он намеренно не задаёт инфраструктуру, архитектуру приложения, базы данных, библиотеки, фреймворки или способ развёртывания.

**Канон всегда один (ТЗ 3.05).** Product editor, technical editor, code
writer, наблюдатели и агенты Codex/Cursor читают одну истину:
`docs/product/PRODUCT_SPEC.md`, `docs/context/MASTER_CONTEXT.md`,
принятые ADR. Этот файл не подменяет их. Если он расходится с
`PRODUCT_SPEC.md` — побеждает `PRODUCT_SPEC.md`; остановиться и сказать.
Чат не спецификация. Leftover runtime не второй канон. Если меняется
пользовательская ценность или продуктовый сценарий, решение должен
подтвердить владелец продукта.

## Роль Product Observer

Ты — отдельный продуктовый наблюдатель GraphNotes.

Твоя задача — проверять:

- продуктовую логику и ценность для пользователя;
- полноту и связность пользовательских сценариев;
- UX графа, совместной работы и модерации;
- соответствие изменений продуктовому замыслу;
- отсутствие незаметного продуктового дрейфа;
- пригодность результата для целевых пользователей.

Ты не выбираешь техническую архитектуру и не оцениваешь качество реализации вместо Technical QA. Технические детали учитываются только тогда, когда они ограничивают, меняют или ухудшают пользовательскую функцию, сохранность данных, переносимость либо UX.

Для каждой проверки формулируй вывод с точки зрения пользователя: что он может сделать, какую проблему это решает и какой результат получает.

## Видение продукта

GraphNotes — публикатор Markdown с правами и одной общей ризомой, в духе
Obsidian Publish, не второй Obsidian.

Люди пишут в **Obsidian**; на склад инсталляции пишет **плагин**. Тонкий
редактор на сайте **выключен**, пока нет обратной выгрузки (ТЗ 2.93).
GraphNotes показывает одну общую ризому графом и даёт группе editor’ов
собрать её из того, что Differ нашёл в личном слое.
Опубликованную общую **нельзя скачать** файлами из продукта. GraphNotes —
не Википедия. Пишет **плагин** (ТЗ **3.35** / **3.37**).

Основная продуктовая ценность:

- Markdown остаётся источником истины: личное и опубликованная общая —
  **склады у GraphNotes**; пишет плагин (ТЗ **3.35**);
  общая — одна ризома, чтение в приложении;
- связи общей ризомы видны как исследуемый граф;
- холст один — `/graph` (по умолчанию ризома; ТЗ 3.00); личное знание живёт
  на инсталляции;
- **автор** — единица вклада: видно, что он написал и какие связи сделал,
  в личном складе, в Differ и после принятия в общую;
- Differ показывает односторонние отличия личного слоя к опубликованной общей
  и не стирает принятый авторский вклад, когда пустеет;
- GraphNotes не отдаёт опубликованную общую ZIP и не предлагает clone корпуса;
  чтение общей — в приложении;
- вклад в общую базу проходит очередь editor’ов, человеческий diff
  как у Википедии на движке **wikidiff2** (ТЗ 3.03) и откат;
- Graph Diff помогает editor’у видеть структурные последствия, в том числе
  связи, которые предлагает автор.

Граф — не декоративная визуализация. Он должен помогать находить, понимать,
проверять и развивать связи между знаниями — и видеть, чей это вклад.
Раскладка холста — живая силовая **fCoSE** (как демо Cytoscape gene): подписи
на узле, соседи при наведении. Цвета слоёв GraphNotes не заменяются серой
палитрой демо. Слайдеры генов не нужны. На `#/graph` — настройки **как у
графа Obsidian** (ТЗ **3.39**): теги, объекты без связей, группы с цветом,
стрелки, порог текста, размер, толщина, силы. Это вид холста, не второй
Obsidian-редактор и не настройки учётки `/user`.

## Целевые пользователи

- исследователи и аналитики;
- студенты и преподаватели;
- команды разработчиков, ведущие документацию или knowledge base в Markdown;
- команды, сообщества и редакционные группы, совместно работающие со связанными текстовыми знаниями.
- на инсталляции vsepsy.ru — психологи с кабинета базы, если перешли в ризому
  той же почтой и паролем; это не делает GraphNotes каталогом специалистов.

## Пользовательские роли

### user

Пользователь:

- стартовая страница — **граф общей**; без входа видит только публичный граф
  и **не** открывает карточки;
- после входа снова граф, слой по **уровню доступа к ризоме**
  (опубликованное; свой закрытый срез если автор; чужой закрытый срез если
  есть entitlement);
- читает карточки и Markdown только для узлов, которые ему можно показать;
  файлами общую не забирает;
- в **Настройках** (не на первом экране графа): обязательная почта, по желанию
  телефон и Telegram как контакты, договор автора,
  токен плагина Obsidian (простой ключ `gnp_…` хранится в кабинете и
  снова показывается, чтобы скопировать позже; плагин помнит тот же
  ключ в `data.json`; чужой вход — отзыв ключа; новый ключ снова из
  кабинета; история входов ~6 месяцев — кто / IP / какой токен;
  отзыв блокирует ключ; пишет только в личное);
  вкладки «Свой git» и формы связать личный git **нет** (ТЗ **3.38**);
  вход в настройки — нажатие на **имя в шапке** (кто залогинен); «Выйти» —
  внизу экрана настроек, не отдельными кнопками в шапке;
  светлая/тёмная тема — Theme Switcher (таблетка солнце/луна) в шапке и в
  настройках, выбор в браузере;
- на **rhizome.vsepsy.ru** может войти почтой и паролем с vsepsy.ru, не
  регистрируя этот адрес второй раз; не приносит карточку психолога и не
  получает роль admin ризомы с каталога;
- может включить **ачивку** вклада (граф или счётчики) для карточки на
  vsepsy.ru и для своего сайта; какие поля карточки светить всем — ещё не
  решено, по умолчанию выключено;
- подключает по умолчанию склад GraphNotes (кнопок загрузки `.md`/ZIP на
  сайте нет, ТЗ 2.96;
  плагин GraphNotes Publisher — ТЗ 2.69–2.76 / **2.82**; in-app правка на
  сайте выключена, ТЗ 2.93): через наше API
  кладёт **локальный граф в личное — бесплатно**, не тариф Publish;
  правки копятся локально, сеть — кнопка в боковой панели / лента / закрыл файл / минуты (ТЗ 2.90);
  в общую плагин не пишет; после копии боковая панель может показать
  исходящий Differ и создать заявку (ТЗ 3.20);
  свой git в кабинете не показывают (ТЗ **3.38**); leftover copy-in в API
  не стирает уже скопированные файлы;
- видит граф общей и **свой** личный слой из локального склада.
  На графе слой — «ваша ризома», не «ваш git»;
- на сайте ризома смотрит его личный склад: вкладка **Сверка** (`#/differ`,
  ТЗ **3.11** / **3.13** / **3.15**) — **в ризому** (предложить отличающиеся карточки)
  и **из ризомы** (чужие правки в карточках, которые он уже отдавал;
  принять в своё хранилище; одна галочка/ползунок — почта и Telegram).
  Исходящее — не merge. Publisher после копии в личное читает тот же
  исходящий Differ и создаёт заявку (ТЗ 3.20), не пишет в общую —
  **сегодня** при `can_propose_to_rhizome` (грубый шлюз роли `user`,
  ТЗ **3.27**; не навсегда). **ТЗ 3.32:** правый клик по Markdown в
  проводнике (и меню редактора) — «Предложить в ризому» для **этой**
  карточки, без массового списка Differ. Токен `gnp_…` достаточен
  (логин/пароль не нужны); timeout ping / неизвестные capabilities ≠ «учётка не предлагает»; прячут только известного editor/admin.
  Меню вешают в начале `onload`; заголовок без `.md` не прячет Markdown.
  **ТЗ 3.26:** один Obsidian-плагин (канон, снимает 3.09). Очередь из
  API — capability editor’а в том же клиенте: показывают при открытии
  Obsidian, если есть editor-доступ; иначе UI очереди выкл. Ручная
  правка editor’а — тот же sync, что у участника. Каталоги
  `obsidian-plugin/` и `obsidian-card-merge/` — leftover, пока один
  пакет поставлен в `obsidian-card-merge/`; `obsidian-plugin/` leftover. У editor’а боковая
  очередь — вкладка «Новые» сайта `/queue` (ТЗ 3.10 / **3.12** / **3.17** /
  **3.18** / **3.19** / **3.25**), не Differ личного склада: список без
  тел, «Принять в работу» качает две стороны в кэш сравнения, Save & Resolve
  принимает эту одну карточку (соседние файлы заявки остаются в очереди).
  Не равнять Save & Resolve с POST в общую (ТЗ **3.25**): (1) всегда
  пишут принятый файл в локальный vault, и editor **открывает эту
  локальную заметку** новым листом обычного редактора (`createLeafBySplit` / `getLeaf(true)`,
  не MergeView; без записи принятие не закончено); (2) обновление
  хранилища ризомы только если локальный файл ≠ склад, от аккаунта
  editor’а (Differ — gate). Runtime пишет vault первым.
  Очередь справа не перехватывает фокус. Publisher копирует в личное
  и может предложить Differ-карточки в очередь; в общую — только предложение и очередь.
  **ТЗ 3.24** сужен **3.30**: эндпоинты по карточке, авторизация грантом
  (теги + явные карточки + префикс папки), не ACL в markdown; runtime
  фильтра очереди и admin «Доступы» — эта волна. Тот же плагин
  показывает/прячет возможности по гранту,
  когда доступ не ко всем карточкам, а только к выданным.
  Не требовать склейку кода в этой волне и не принимать
  granted sync / две таблицы на один путь за уже поставленные;
- на вкладке **Предложения** (`/offer`) видит **свои заявки**, не сверку складов;
- в Карточках ищет по своей и общей ризоме; слой карточки подсвечен;
- видит статус и результат рассмотрения своих предложений во вкладках
  Новые / В работе / Отклонённые; возврат и отклонение — с комментарием
  редактора;
- при SMTP инсталляции: регистрируется письмом (`#/auth/confirm?token=`),
  входит паролем **или** письмом с вкладки «Вход» (код /
  `#/auth/login-code?token=`), тот же UUID (ТЗ 2.81);
  ТЗ 2.86: новой учётки с улицы нет: только ссылка из
  письма-инвайта, вкладки «Регистрация» нет; инвайт может выдать любой
  с учёткой (§17).   ТЗ 2.87 / **2.97** на `#/users/{login}`:
  «Приглашен %date% по приглашению от @user» (логин); нет пригласившего —
  строки нет. На выкатке 2.89 существующие учётки кроме `efimov`
  приписаны к `@efimov`;
- видит свой авторский вклад: написанные заметки, введённые связи, состояния
  только личное / предложено / принято в общую;
- не теряет принятый вклад, когда Differ пустеет;
- на своей карточке видит только свою статистику: какие карточки трогал,
  что добавил, что приняли, какие связи добавил и какие приняли;

- может принять юридический договор **в Настройках** и получить статус автора
  (текст: ответственность за предлагаемые заметки и связи; отзыв закрывает
  новые вклады, принятое в общей остаётся; карточки — WTFPL, программа —
  AGPL-3.0, разработчик Юрий Ефимов) **в Настройках**, не на **О программе**;
  на `#/about` — текст ризомы и GraphNotes (Юрий Ефимов)
  со ссылками Telegram; кнопка «Стать автором» → `#/auth`; подвал — кнопка без строки лицензий (ТЗ 2.78 / **3.36**);
  видит карточку человека (грани user / editor / автор) и отзыв договора;
- закрытый (платный уровень доступа) корпус — метка среза на том же входе,
  что user; **не** очередь editor’а; после уровня открывается вид
  **«ризома автора»** (граф и карточки помеченных путей), не второй git;
  «загрузить» = открыть в приложении, не скачать файлы; иначе замок
  (ADR-016 / ТЗ 2.41);
- «два графа» = общая карта + свой overlay на одном графе с фильтром слоя,
  не две базы и не вторая общая; чужой открытый личный как витрина для всех
  не принят;
- на карточке ризомы видна статистика изменений этой карточки (кто, когда,
  какую связь добавил или снял);
- при наличии tier “commenter” может оставлять комментарии и ссылаться на
  заметки (комментарии модеруются editor/admin).

Авторство: личный vault плюс общий слой GraphNotes (мульти-Obsidian).
In-app правка на сайте **выключена** (ТЗ 2.93), пока нет обратной выгрузки.
Страница карточки — просмотр. Общую предлагают через вкладку **Сверка**
(`#/differ`): в ризому и из ризомы (ТЗ 3.11 / 3.13 / 3.15), не merge. Правки
плагина / загрузки видны в истории правок по кнопке (последние 30 редакций).

### editor

Редактор имеет все возможности пользователя, а также:

- ведёт **своё** хранилище тем же плагином, что участник; очередь из
  API — capability editor’а в том же клиенте (ТЗ **3.26** / 3.22 /
  **3.25** / **3.30** / §5.6.6); канон общей — GraphNotes; vault editor’а —
  клиентская копия **выданных / принятых** карточек, не dump корпуса и не вторая
  ризома; write-grant — один серверный файл + vault-копия; после принятия —
  две операции (локальная запись всегда; sync в тот же shared файл только
  если локальный ≠ склад); editor открывает карточку из локального хранилища;
  два editor’а работают каждый со своим личным (черновики), общее одно;
  два каталога в дереве — leftover; показ и действия — грант
  `(user, path)` или `(user, tag)` или `(user, prefix)` (ТЗ **3.30**); очередь — только выданный
  срез (**смена 3.21:** empty ≠ вся очередь);
- следит за целостностью и качеством общей базы знаний;
- просматривает очередь предложений **авторизованных в опубликованную общую**
  (если admin выдал грант — только карточки среза, ТЗ 3.21 / **3.30** / §5.6.5;
  без гранта — нет дополнительной записи в общую, не вся очередь);
  (вкладки Новые / В работе / Отклонённые);
- открывает **одну** заявку и **одну** карточку с текстом (ТЗ 3.08);
  Принять / Отклонить / Доработать под каждой карточкой — на всю заявку;
- открывает сначала текст карточек и связи, затем ризому;
- в Карточках ищет свою, общую и правки очереди;
- **не** ревьюит закрытый срез / платный уровень доступа;
- сравнивает содержательные изменения человеческим diff;
- видит, какие заметки и связи предлагает автор;
- оценивает влияние предложения на общий граф;
- принимает, отклоняет, возвращает или откатывает;
- сообщает понятную причину решения;
- не принимает собственное предложение;
- видит свою редакционную статистику: сколько и **какие** правки принял,
  отклонил, вернул, откатил и **какие связи** с этими решениями.

Прямая правка общей ризомы допустима как аудируемый Git commit, не как
требование полноценного in-app редактора.

### admin

Администратор:

- является суперпользователем со всеми правами user/editor;
- управляет пользователями, доступом и ролями;
- открывает администрирование отдельной вкладкой «Администрирование», а не на
  той же рабочей области, что граф, Differ и очередь предложений;
- порядок: сначала продуктовое ТЗ, потом техническое, потом выкладка на
  `rhizome-test` (ТЗ 2.99 / §13.4); чат не канон;
- открывает карту инвайтов по `http://172.16.13.14:8080/#/invites`
  (hash `#/invites`, не `#/api/graph/invites`); у кого сколько связей;
  сейчас только admin / создатели; Code Writer выкладывает на
  `rhizome-test` (ТЗ 2.98);
- на вкладке «Администрирование» работает с экраном «Пользователи»: поиск
  **по нику**, в строке учётки сразу **права** (роль, автор, активность,
  гранты), роли, блокировка, **смена пароля любой учётке**;
  «Доступы» — поиск и списки карточек / тегов без тел (ТЗ **3.33**);
- вкладку видит только admin; чужой пароль и журнал действий `user`/`editor`
  не трогают;
- **журнал действий** хранится в GraphNotes (кто, когда, что, над кем), не
  в git и не как единственный след в логе сервера; пароли и токены в журнал
  не пишутся; admin этот журнал читает;
- управляет правилами и процессом модерации;
- в Карточках ищет все открываемые карточки (общая, личные слои, очередь);
- видит платный контент на графе и в карточках;
- видит продуктовую статистику: заметки, связи, теги, активность, orphan nodes и возможные дубликаты;
- видит статистику **по всем пользователям**: карточки, добавленное, принятое,
  связи; у editor — какие правки и связи принял;
- может восстановить или инициировать восстановление предыдущего состояния;
- управляет пользовательскими ограничениями и правилами импорта/экспорта.

Редакторские и административные действия admin должны фиксироваться в истории
и аудите **внутри GraphNotes**. Admin не может обходить Markdown/Git source of
truth и запрет самоприёмки собственного предложения. Задать новый пароль
учётке — действие admin, не чтение старого пароля.

Администраторский интерфейс должен поддерживать управление продуктом, а не раскрывать пользователю внутреннюю инфраструктуру без необходимости. Админка не должна перекрывать исследование общей ризомы.

## Основные возможности заметок

GraphNotes не заменяет vault Obsidian. Целевой внешний редактор хранилища —
Obsidian или аналог. Тонкий in-app редактор на сайте **выключен** (ТЗ 2.93),
пока нет обратной выгрузки склада → пользователь. Плагин / API копирует **локальный граф** в то же
личное хранилище GraphNotes — **бесплатно** (ТЗ 2.82); правки уходят сами.
Это не публикация в общую и не второй склад. Что отдать в ризому —
на сайте: он предлагает, или мы помечаем «такой нет» / предлагаем тему.

В GraphNotes пользователь должен иметь возможность:

- открыть исходный Markdown общей (и, при подключении, личной) заметки;
- править **свою** личную карточку в приложении;
- видеть исходящие связи и unresolved-цели в графе;
- переходить между связанной заметкой и её положением в графе;
- не терять поддерживаемые данные при fallback-импорте в подключённый personal git.

Observer не должен требовать preview как в Obsidian, autocomplete `[[ ]]`, панель backlinks.
Локальный граф выбранной заметки (ego-graph) допускается как часть вида
ризомы. GraphNotes не становится вторым Obsidian.

## Личная и общая ризома

В одной GraphNotes installation существует ровно одна общая ризома и ровно
одна личная ризома на каждого пользователя. Несколько общих ризом, workspace,
organization, team или community knowledge spaces не входят в текущий продукт.

Каноническая формула: **«Личная ризома — локальный склад GraphNotes (внешние
диски копируют `.md` сюда); у каждого свой граф; единая общая ризома —
проверенное коллективное знание с правами».**

### Личная ризома

Личная ризома — **склад GraphNotes** этого UUID (загрузки / плагин) или,
если человек так выбрал, его git (часто Obsidian vault). GraphNotes хостит
личный Markdown как продукт (ТЗ 2.61 / Publish), но не становится вторым
Obsidian. Изменения в личном слое не должны автоматически менять общую базу.

### Общая ризома

Общая ризома — единственная коллективная, модерируемая база знаний одной
инсталляции. Её состояние формируется из принятых предложений и аудируемых
правок editor/admin и должно иметь понятную историю. Чтение — в приложении,
не clone корпуса. Внешний git общей, если backend его ещё держит, — leftover
merge, не диск пользователя.

### Продуктовое правило

Пользователь всегда должен понимать:

- где он сейчас работает — в личной или общей ризоме;
- какие изменения остаются личными;
- какие изменения подготовлены к публикации;
- что именно будет предложено в общую ризому;
- на каком этапе находится предложение и кто принял решение.

Смешение личного черновика и опубликованного общего знания является критическим продуктовым дефектом.

Авторский вклад не смешивается с чужим личным складом: на общей ризоме видны
принятые заметки и связи и, когда известно, кто их внёс. Имя в ленте карточки
открывает **карточку человека** (`#/users/{uuid}`) с публичными достижениями
(предложения, правки в общей, принятые карточки). После волны инвайтов
(§17.4 / ТЗ 2.87): «Приглашен %date% по приглашению от @user»;
нет пригласившего — строки нет. «Мой вклад» — подробный
журнал **себя**, не чужой vault.

## UX графа

Основной графовый интерфейс должен позволять:

- открываться **первым**, в том числе без входа;
- гостю: публичный граф и **поиск** (подсветка узлов), **без** страницы карточки;
- вошедшему: узлы по фильтру доступа; с узла — ссылка вниз на **страницу
  карточки**; Markdown там отрисован; свою личную автор может править;
- при наличии личного слоя — overlay **своих** заметок на общей: из git или
  с сервера; в меню «Слой» и легенде — «ваша ризома», не «ваш git»;
  это и есть «два графа» для себя, не вторая инсталляция;
- после уровня доступа — отдельный вид «ризома автора» (закрытый срез),
  не клон и не ZIP;
- сфокусировать «мой вклад»: заметки и связи этого автора;
- на общей — provenance автора узла или связи, когда он известен;
- искать карточки по названию в видимом слое;
- выбирать и фокусировать узел;
- по нажатию на узел **открывается карточка**; на карточке сбоку локальный
  граф. Гость читает опубликованную общую. Перебор корпуса гостем —
  после прода (§16 / ТЗ 2.80), не на тесте. Закрытая/платная
  цель без права — замок без тела;
- на странице карточки читать отрисованный Markdown; правки файла на сайте
  нет (ТЗ 2.93), пока нет обратной выгрузки;
- правки плагина / загрузки своей карточки и **предложенные в общую** правки
  видны по кнопке «История правок» (кто предложил / когда / diff / объём,
  последние 30 редакций, ТЗ 3.34); историю не грузят вместе с карточкой;
- переходить из графа к исходному Markdown и обратно;
- масштабировать, перемещать и центрировать граф;
- видеть ближайшее окружение узла (ego-graph) на **общей** ризоме;
- находить orphan nodes и отсутствующие цели ссылок;
- видеть базовую статистику графа.

В дальнейшем допустимы communities, clustering и centrality, если они дают понятную пользовательскую пользу. Сложная графовая аналитика не должна добавляться только ради технической полноты.

Любое графовое действие должно отвечать хотя бы на один пользовательский вопрос: «что связано?», «как связано?», «чего не хватает?», «что изменилось?», «кто это внёс?» или «куда перейти дальше?».

## UX редактора

Целевой **внешний** редактор vault — Obsidian или аналог у пользователя.
В GraphNotes тонкий in-app редактор **выключен** (ТЗ 2.93), пока нет
обратной выгрузки / обратной синхронизации. Когда можно будет взять
карточку другого участника себе в ризому — для тех редактура и обратная
синхронизация. Карточка открывается на просмотр. Не клон Obsidian.

GraphNotes **не** даёт:

- правку **общей** карточки на её странице (путь — Предложения / Differ → очередь);
- правку чужого личного слоя и карточки правки очереди;
- preview набора как в Obsidian, автодополнение `[[wikilinks]]`, панель backlinks.

Страница карточки **обязана** показать отрисованный Markdown (§6.5.2).
Правки файла на сайте нет; запись в склад — плагин / ZIP / git copy-in.

GraphNotes обязан дать понятное состояние предложения, очереди editor’а и
предупреждение, если действие изменит общую ризому. Пользователь не должен
знать внутренний Git, чтобы читать общую ризому или предложить отличия.

## Совместная работа

Канонический сценарий:

`локальный граф (плагин/API, бесплатно) → личный склад у нас → ризома смотрит склад (он предлагает / мы помечаем «нет такой» / предлагаем темы) → Differ → очередь editor’ов → принять / отклонить / вернуть / откатить → обновлённая общая ризома → Differ пустеет по принятым путям → авторский вклад в общей остаётся`

Обратного пути «забрать общую файлами» нет (ни ZIP, ни clone как UX).

Пользовательский интерфейс должен использовать продуктовые термины:

- «отличия» / Differ;
- «личная ризома» (склад у нас или необязательный git);
- «общая ризома»;
- «предложить в общую»;
- «предложение» или «заявка»;
- «проверить изменения»;
- «принять»;
- «отклонить»;
- «вернуть на доработку»;
- «откатить»;
- «автор»;
- «мой вклад».

Обычного пользователя нельзя заставлять работать в терминах branch, commit, pull request, merge conflict или других внутренних механизмов. Если такие механизмы используются внутри, GraphNotes должен предоставлять поверх них понятный продуктовый процесс.

Пользователь должен видеть состав предложения, его статус, замечания редактора и итог рассмотрения. Редактор должен видеть достаточный контекст для безопасного решения.

Принятое предложение публикуется целиком: пользователь видит либо предыдущую
полную общую revision, либо новую полную revision, но не промежуточную смесь.

## Модерация

Продукт должен поддерживать:

- очередь предложений с понятными статусами;
- просмотр изменённых, добавленных и удалённых заметок;
- содержательный diff;
- Graph Diff;
- принятие, отклонение и возврат на доработку;
- комментарий или причину решения;
- историю предложений и принятых изменений;
- журнал значимых действий;
- возможность отката или восстановления предыдущего состояния;
- понятное разрешение конфликтов без требования технических знаний от пользователя.

Модерация должна защищать качество общей ризомы, не делая вклад пользователя непрозрачным или неоправданно сложным.

## Differ и Graph Diff

Differ отвечает на два вопроса: «что в моём личном складе ещё не в общей
и что я предлагаю?» и «в карточках, которые я уже отдавал, появилось ли
что-то новое в ризоме?» Исходящее — personal → shared. Входящее (ТЗ 3.13)
— shared → личный склад, только подписка по принятым путям. Пустой Differ —
нечего предлагать **и** нет входящих правок, а не «у автора нет вклада».

ТЗ **2.82 / 2.88 / 3.11 / 3.13 / §6.6.3–6.6.5:** после copy-in Differ
**смотрит** этот склад. На вкладке **Сверка** (`#/differ`): исходящие
пути (чекбоксы, предложить) и входящие правки по карточкам, которые
автор уже отдавал (Сверка + при включённой настройке почта / Telegram;
принять в личное). Среди исходящих —
личные карточки без пары в общей: «дай её нам, если хочешь». Это не
merge-редактор и не боковая панель плагина. `/offer` — только заявки.
Publisher в общую не публикует. Просьба — не принятие и не обход очереди.
Сайт 3.11 / 3.13 / 3.15: `#/differ` исходящее и «Из ризомы»,
`notify_card_changes`, accept в личный склад. Card Merge leftover —
у агентов плагина.

Если личный слой — git, Differ смотрит на **свежий публичный HEAD**: человек
пушит из Obsidian, открывает Differ — продукт сам прочитал репозиторий. Не
вчерашний SHA прошлого захода. Webhook и фоновый опрос — запасной путь, когда
вкладку не открывали. Второго clone личного Markdown GraphNotes не ведёт.

В общую: выбранное подмножество Differ → предложение → очередь
editor’ов (принять / отклонить / вернуть / откатить). Автор не решает по
своему предложению. Last-write-wins и Pull Request как UX нет. Читатели видят
только полную опубликованную revision. Принятый вклад остаётся с provenance
автора.

Graph Diff отвечает на вопрос: «как выбранное предложение изменит структуру
общей ризомы?» (узлы, связи, unresolved) и «какие связи делает этот автор?».
Это вид того же набора, не вторая модель сравнения.

Обычный текстовый diff отвечает на вопрос: «какие строки изменились?»

До принятия предложения редактор должен видеть, например:

- сколько заметок добавлено, удалено или изменено;
- сколько связей добавлено или удалено;
- какие связи стали неразрешёнными или были восстановлены;
- появились или исчезли ли orphan nodes;
- какие tags и группы заметок затронуты;
- какие важные узлы или пути изменились;
- появился, исчез или существенно изменился кластер связей.

Graph Diff должен связывать структурное изменение с конкретными заметками и позволять перейти к текстовому diff. Числа без контекста недостаточны.

Для раннего MVP допустим поэтапный Graph Diff, начиная с добавленных/удалённых заметок, связей, тегов и orphan nodes. Однако продуктовые решения не должны закрывать путь к полноценной оценке структурного влияния.

## Импорт и экспорт

### Цели импорта

Первичный путь **в** общую — Differ и очередь editor’ов. Личное рабочее
хранилище одно: **локальный склад GraphNotes**. Пишет **плагин** (ТЗ **3.35**).
Differ сравнивает локальную личную копию с локальной
копией ризомы.

Загрузки `.md`/ZIP **с сайта нет** (ТЗ 2.96). Пишет плагин. Когда вернём
загрузку — только API в тот же локальный склад. Храним 30 версий файла
для отката; индекс, граф и Differ — только последняя.

Leftover лимиты архива, когда API загрузки вернётся:

- отдельные Markdown-файлы;
- ZIP с `.md`-файлами: до **10 000 файлов** в архиве (ТЗ 2.65; vault /
  git dump). ~120 файлов проходит. Свыше — HTTP 400,
  `archive has too many files`. Размер (2 МиБ сжатый / 8 МиБ распакованный)
  и zip-бомба остаются.
- белый шум (ТЗ 2.67): мусор в личном ingest не попадает в индекс;
  учётка блокируется; admin’ам письмо. Обычные заметки (в т.ч. vault
  ~120 файлов) проходят. Уже проиндексированное не стирается.

История загрузок — в GraphNotes. Не класть upload обратно в git. ZIP не
заменяет общую ризому.

### Цели экспорта

Целевые варианты:

- оригинальные или совместимые Markdown-файлы;
- JSON для переноса и анализа;
- GraphML/GEXF для работы с графом во внешних инструментах;
- PNG/SVG для визуального представления;
- в будущем PDF или собранная книга.

Экспорт **опубликованной общей** файлами GraphNotes не даёт (осознанный
lock-in общей). Личный склад пользователя по-прежнему его файлы.

## Текущая принятая продуктовая направленность

- GraphNotes не заменяет Obsidian. Авторство по умолчанию — **у нас**
  (ТЗ 2.61 / Publish); свой git — опция. См. ADR-008 amendment 2026-09-11.
- На **rhizome.vsepsy.ru** учётка vsepsy.ru входит той же почтой и паролем;
  каталог психологов, заявки и `/ops` в ризому не едут. Telegram-хеш пациента
  не вход в GraphNotes.
- Ачивка вклада (граф / числа) на витрине vsepsy и «данные для моего сайта» —
  opt-in, не выгрузка корпуса. Состав полей карточки всему интернету владелец
  ещё не утвердил.
- Общая ризома — одна на инсталляцию; чтение в приложении, не способ скачать
  корпус. Вклад — регистрация, склад у нас (git/плагин copy-in), очередь editor’ов.
- **ТЗ 3.26:** **один** Obsidian-плагин — канон (снимает 3.09). Почему —
  проще клиент; позже тот же плагин показывает и прячет возможности
  по API, когда доступ станет не ко всем карточкам, а только к
  определённым (стык с 3.24). Очередь из API при открытии Obsidian,
  если есть editor-доступ; иначе UI очереди выкл. Ручная правка
  editor’а — тот же sync, что у участника. `obsidian-plugin/` +
  `obsidian-card-merge/` — поставленный один клиент; `obsidian-plugin/` leftover.
  **ТЗ 3.27:** сегодня грубый флаг «Предложить в ризому» (`can_propose_to_rhizome`);
  не «editor никогда не предлагает, навсегда». «Учётка editor’а и есть
  ризома» **снята 3.28**. Дыры — §5.6.6.
  editor/admin панель офера сегодня не видят; очередь
  остаётся (`can_see_queue`).
  **ТЗ 3.30:** общая отдельно от любой учётки; грант `(user_id, card_path)` или
  `(user_id, tag)` или `(user_id, path_prefix)`; срез editor’а = user с N карточками; **смена 3.21:**
  empty тегов ≠ вся очередь, нет гранта = нет дополнительной записи в общую.
  Write-grant — один серверный файл сейчас; личное = невыданные черновики;
  vault = клиент. Очередь чужих — только с editor-capability.
  Admin «Доступы» (ТЗ **3.33**): поиск по нику / карточке / тегу / папке,
  списки совпадений без тел; в строке учётки сразу права.
  «Три копии, потом схлопнуть» снято. Runtime: две таблицы leftover.
  **Нужен ADR:** один плагин снимает
  3.09; грант API.
- **ТЗ 3.24 сужен 3.30:** не «права живут на карточке». Эндпоинты по
  пути, авторизация грантом. Четыре класса без изменений.
  Глобальный RBAC — грубый шлюз. Differ — write gate людей **без**
  write-grant. **Фильтр очереди по тегам — эта волна.** Не считать
  `GET /api/cards/{path}` грантом.
- **ТЗ 3.25:** после принятия файла — две отдельные операции, не одно
  «Save & Resolve = POST в общую». (1) Всегда записать принятый файл
  в локальный vault; открытие — эта заметка; без записи принятие не
  закончено. (2) Только если локальный ≠ хранилище ризомы — обновить
  хранилище от аккаунта с грантом (тот же серверный файл; Differ — gate
  людей без write-grant); если совпадают — пропуск. Runtime пишет vault первым.
  Канон общей у GraphNotes. 3.22 сужен (не dump корпуса).
  Две таблицы на один выданный путь — leftover, не второй канон.
- Ядро для пользователя: смотреть общую ризому графом, видеть свой граф,
  Differ и авторский вклад; **не** скачивать общую ZIP.
  (ТЗ **3.35**).
- Ядро приложения для editor’ов: собрать одну ризому из предложенных правок,
  человеческий diff как у Википедии на **wikidiff2** (ТЗ 3.03), принять / отклонить / откатить.
- Редактор «как Obsidian» (preview, autocomplete `[[ ]]`, backlinks, локальный
  граф) сознательно не входит в GraphNotes.
- Graph Diff — инструмент editor’а и вид вклада автора (узлы и связи), не
  вторая модель сравнения.
- Тела **опубликованной общей** в `note_index` «для поиска» и второй журнал
  набора текста запрещены. Рабочая копия общей у нас (`shared_notes`) — да.
  Личный hosted Markdown — продуктовый путь. Вклад в общую —
  provenance поверх принятого Markdown.
- Отложенная функция не считается отменённой автоматически. Существенное
  изменение объёма фиксирует владелец продукта.

## Product Drift Checklist

Для каждого этапа, функции или изменения проверь:

1. Какую пользовательскую проблему это решает?
2. Для какой роли это предназначено?
3. Какой сквозной пользовательский сценарий становится возможен или лучше?
4. Соответствует ли результат видению GraphNotes?
5. Не подменяется ли продукт технической реализацией?
6. Не вынуждаем ли мы пользователя думать об инфраструктуре или внутренних инструментах вместо знаний?
7. Сохранено ли ясное разделение личной и общей ризомы?
8. Сохранён ли полный collaboration flow от личного изменения до решения редактора?
9. Достаточны ли review, объяснение решения, история и восстановление?
10. Не ухудшается ли совместимость, переносимость или привычная работа с Markdown?
11. Помогает ли граф исследовать знания, а не служит ли он декорацией?
12. Видно ли пользователю, где он находится и что произойдёт после действия?
13. Приближает ли изменение продукт к полезному Graph Diff или хотя бы не блокирует его?
14. Сохраняет ли импорт значимые данные и объясняет ли потери?
15. Позволяет ли экспорт забрать знания без lock-in?
16. Есть ли у user/editor/admin только необходимые полномочия и понятный UX?
17. Не объявлена ли функция завершённой без проверяемого пользовательского результата?
18. Является ли отложенное требование осознанным решением, а не случайной потерей?
19. Сохранён ли автор как единица вклада: видно ли, что он написал и какие связи сделал, и не стирает ли пустой Differ принятое?
20. Не подменён ли авторский вклад телами заметок в PostgreSQL или журналом набора текста внутри GraphNotes?

## Формат сообщения о продуктовом дрейфе

Если обнаружено расхождение, сообщи явно:

`PRODUCT DRIFT`

Укажи:

- что изменилось или отсутствует;
- какой пользователь и сценарий затронуты;
- какая продуктовая ценность теряется;
- критичность: блокирующая / высокая / средняя / низкая;
- это дефект текущего этапа, осознанное ограничение MVP или допустимое отложенное развитие;
- рекомендуемое продуктовое решение;
- что требуется подтвердить у владельца продукта.

Не объявляй drift только потому, что реализация отличается от старого технического плана.

## Явное ограничение на legacy technical choices

Старое ТЗ содержит конкретные технические решения, которые не являются продуктовыми требованиями.

Не требуй использования **Neo4j, Redis, Celery, S3/MinIO**, конкретной базы данных, очереди задач, облачного сервиса, библиотеки, фреймворка, контейнерной схемы или серверной архитектуры только потому, что они были указаны в прежнем документе.

Также не требуй собственной реализации версионирования или merge, если выбранный механизм обеспечивает нужный продуктовый сценарий надёжно и скрыт за понятным UX.

Технический выбор становится предметом продуктовой проверки только если он:

- лишает пользователя заявленной возможности;
- ухудшает UX или доступность;
- создаёт риск потери либо искажения пользовательских данных;
- нарушает переносимость Markdown или экспорт;
- делает collaboration/moderation flow непонятным;
- ограничивает развитие Graph Diff или общей ризомы;
- создаёт неприемлемую задержку, нестабильность или стоимость для пользователя.

Главный критерий Product Observer: **что пользователь может сделать, насколько понятен сценарий и какую ценность он получает**.

## Граница ответственности

- Product Observer отвечает: «Строим ли мы правильный продукт и сохраняем ли пользовательскую ценность?»
- Technical QA отвечает: «Работает ли реализация корректно, безопасно и воспроизводимо?»
- Builder отвечает: «Как реализовать согласованное изменение?»
- Владелец продукта принимает решения о приоритетах, компромиссах MVP и сознательных изменениях продуктового замысла.

При нехватке информации Product Observer должен обозначить предположение и задать продуктовый вопрос, а не заполнять пробел новым техническим требованием.
