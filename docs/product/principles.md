## 3. Неподвижные продуктовые принципы

### 3.1. Markdown - источник истины

Каноническое знание хранится в Markdown. Узлы, связи, теги, поисковый индекс и
визуальный граф являются производными данными.

```text
Markdown в Git
  -> parser
      -> PostgreSQL index
          -> Graph API
              -> Web UI
```

Поисковый индекс той же природы: сейчас в PostgreSQL, следующая итерация —
Elasticsearch (ADR-015). Не второй канон Markdown.

Запрещено вводить параллельный канонический `graph.json`. Слиянию и
версионированию подлежит Markdown; после изменения Git-состояния граф
переиндексируется.

### 3.2. Личный и общественный слои

- в одной инсталляции существует ровно одна общая ризома;
- у каждого пользователя **ровно одно** личное хранилище: **либо** его git,
  **либо** загрузки `.md`/ZIP, не оба сразу (§6.3);
- личный слой — Markdown в этом единственном хранилище, не vault в PostgreSQL
  и не обязательная ветка `user/<uuid>` на общем репозитории;
- общий слой содержит утверждённое коллективное знание в одном knowledge
  repository (ADR-007);
- личный граф — проекция личного слоя (git **или** загрузки, не оба) плюс
  связи с общей ризомой; не отдельный файл;
- общественный граф — проекция утвержденного Markdown общей ризомы;
- сравнение слоёв — **Differ**: односторонние отличия **текущего** личного
  хранилища к опубликованной общей (ADR-009). «Текущее» при подключённом git —
  HEAD после того, как GraphNotes сам прочитал публичный репозиторий (открытие
  Differ, предложение, webhook или фоновый опрос), а не SHA прошлого захода.

Общая — всегда git. Личное — git **или** файлы, не оба. Это не две таблицы
заметок. Workspace, organization, team, community и несколько общих ризом
не входят в текущую модель.

Каноническая формула: **«Личное — одно хранилище на человека (git XOR
файлы); единая общая ризома — проверенное коллективное знание в одном
репозитории».**

### 3.3. Автор — единица вклада

- автор в продукте — внутренний UUID GraphNotes, не GitHub-login как
  пользовательская идентичность;
- человек пишет в своём git; GraphNotes не становится журналом набора текста и
  не хранит канонические тела заметок в PostgreSQL;
- продукт обязан сохранять и показывать **авторский вклад**: какие заметки
  человек написал, какие связи ввёл, в каком состоянии они сейчас
  (только личное / предложено / принято в общую);
- после принятия вклад не исчезает вместе с Differ: он остаётся в общей ризоме
  с provenance автора **и** в ленте взаимодействий с общей;
- создать связь в общей = зафиксировать, **кто** соединил две карточки;
  это статистика человека, не побочный эффект парсера;
- чужой личный git не показывается как «ризома другого автора»; на общей видны
  принятые заметки и связи и, когда известно, кто их внёс;
- вид «ризома автора» после уровня доступа — только **помеченный закрытый
  срез**, не весь чужой личный git и не вторая общая (§5.6.4). Открытый
  чужой личный как публичная витрина (искать и комментировать всем) не
  принят, пока нет отдельного решения владельца и ADR.

### 3.4. GitHub скрыт за продуктовым UX

GitHub используется как внешний Git-движок для репозиториев, веток, коммитов,
истории, diff, Pull Request и merge. Обычный пользователь работает с понятиями
«личная ризома», «общая ризома», «отличия», «предложить в общую»,
«принять / отклонить / откатить», «автор», «мой вклад» и «карточка человека»,
а не с branch, SHA и Pull Request. **Стартовая страница — граф общей
ризомы** (и без входа). Форма «владелец/имя репозитория» не первый экран:
свой git подключают в **Настройках** ([user-settings.md](user-settings.md) §5.5).
Кто какой слой графа и карточки видит — [access.md](access.md) §5.6.

### 3.5. Граф не является границей безопасности

Разделение веток или визуальных слоев само по себе не обеспечивает изоляцию.
Права проверяются backend на основании внутреннего UUID пользователя и
глобальной роли. Credentials GitHub App пользователям не выдаются.

Действия записи через приложение (подключить git, предложить из Differ,
editor) требуют аккаунта. Гость на стартовом графе карточки не открывает
(§5.6). GraphNotes **не отдаёт** опубликованную общую
файлами (нет ZIP «Скачать», нет clone корпуса как UX). Knowledge repository
нужен backend как Git-источник истины, не как способ забрать ризому.
Чтобы «нельзя скачать» выполнялось, корпус общей не публикуется как
продуктовый download/clone. Чтение общей — граф и карточки в приложении.
