## 3. Неподвижные продуктовые принципы

### 3.1. Markdown - источник истины

Каноническое знание хранится в **Markdown**. Узлы, связи, теги, поисковый
индекс и визуальный граф — производные.

```text
.md (Obsidian vault → плагин / API → локальный склад GraphNotes)
  -> parser
      -> PostgreSQL index
          -> Graph API
              -> Web UI
```

Рабочая копия Markdown — **всегда** склад инсталляции GraphNotes: личный
слой и опубликованная общая. **ТЗ 3.35 / 3.37:** в склад пишет **плагин**.
Внешний git-хостинг и форма «Свой git» в кабинете — leftover, не канон. Позже Dropbox / Google
Drive — только если будет отдельное решение и только как коннектор в тот же
склад. Поисковый индекс той же природы: сейчас в PostgreSQL `note_index` (SQL).
Следующая итерация — Elasticsearch (ADR-015 / ТЗ 2.83): начинается
**только после первой утверждённой выкатки на production `rhizome`**.
Не второй канон Markdown и не «положить тела в индекс, чтобы поиск был
быстрее». Выгрузка своей части — с локального склада `.md`, не сборка из
индекса.

Запрещено вводить параллельный канонический `graph.json`. Слиянию и
версионированию подлежит Markdown; после изменения склада граф
переиндексируется.

### 3.2. Личный и общественный слои

- в одной инсталляции существует ровно одна общая ризома;
- у каждого пользователя **ровно одно** личное рабочее хранилище: локальный
  склад GraphNotes. Пишет **плагин** (ТЗ **3.35**). Внешний git —
  leftover, не второй канон; **по умолчанию человек работает у нас**;
- личный слой — Markdown в этом единственном хранилище; холст один —
  `/graph` (по умолчанию ризома; ТЗ 3.00);
- общий слой — утверждённое коллективное знание **одной** ризомы, только в
  приложении, с правами (SPEC **3.40** / MASTER §5.1, §5.6);
- личный граф — проекция личного слоя плюс связи с общей; не отдельный файл;
- общественный граф — проекция утвержденного Markdown общей ризомы;
- сравнение слоёв — **Differ**: отличия **локального** личного склада и
  опубликованной общей (ADR-009 / ТЗ 3.11 / **3.13**). На сайте вкладка
  **Сверка**: предложить в ризому **и** принять чужие правки в карточки,
  которые автор уже отдавал. Не merge. Differ читает склады у нас (ТЗ **3.35**).

Общая читается в приложении. Личное — **копия у нас**, которую принёс
плагин. Workspace, organization, team, community и несколько общих ризом
не входят в текущую модель.

Каноническая формула: **«Личное — локальный склад GraphNotes (пишет плагин
Obsidian); у каждого свой граф; единая общая ризома — проверенное
коллективное знание с правами, как Publish плюс очередь editor’ов. Не
Википедия.»**

### 3.3. Автор — единица вклада

- автор в продукте — внутренний UUID GraphNotes, не логин внешнего хостинга
  как пользовательская идентичность;
- человек пишет во внешнем vault; на склад пишет **плагин** (загрузки с
  сайта нет, ТЗ 2.96); тонкий
  in-app редактор на сайте **выключен**, пока нет обратной выгрузки (ТЗ 2.93).
  Плагин/API копирует `.md` на склад (вход локального графа —
  бесплатно, ТЗ 2.82); разговор «что отдать в общую» — на сайте ризомы, не
  публикация из Obsidian;
  GraphNotes не становится журналом набора текста; тела **опубликованной
  общей** не копируют в PostgreSQL в обход Differ;
- продукт обязан сохранять и показывать **авторский вклад**: какие заметки
  человек написал, какие связи ввёл, в каком состоянии они сейчас
  (только личное / предложено / принято в общую);
- после принятия вклад не исчезает вместе с Differ: он остаётся в общей ризоме
  с provenance автора **и** в ленте взаимодействий с общей;
- создать связь в общей = зафиксировать, **кто** соединил две карточки;
  это статистика человека, не побочный эффект парсера;
- чужой личный склад не показывается как «ризома другого автора» всем подряд;
  на общей видны принятые заметки и связи и, когда известно, кто их внёс;
- вид «ризома автора» после уровня доступа — только **помеченный закрытый
  срез**, не весь чужой личный слой и не вторая общая (§5.6.4). Открытый
  чужой личный как публичная витрина (искать и комментировать всем) не
  принят, пока нет отдельного решения владельца и ADR.

### 3.4. Знание живёт у нас (ТЗ 3.35 / 3.37)

Знание — Markdown + Obsidian + плагин. GraphNotes — не Википедия и не
MediaWiki как продукт.

Внешний git-хостинг в живом каноне **не участвует**: не склад, не коннектор,
не merge-движок, не API на горячем пути. Продукт — хостинг графа и карточек
на инсталляции (как Obsidian Publish), со своими правами.

Leftover (недописанный код, не канон): copy-in из
личного git (кабинет «Свой git» снят, ТЗ **3.38**), merge-out после accept.
Обычный пользователь работает с «личная ризома», «мой граф», «общая ризома»,
«отличия», «предложить в общую», «принять / отклонить / откатить», «автор»,
«мой вклад» и «карточка человека», а не с branch, SHA и Pull Request.
**Стартовая страница — граф общей ризомы** (и без входа).
Кто какой слой графа и карточки видит — [access.md](access.md) §5.6.

Старые ADR, где внешний git-хостинг ещё назван движком знания, leftover:
побеждает это ТЗ. ADR в этой поставке не переписывать.

### 3.5. Граф не является границей безопасности

Разделение веток или визуальных слоев само по себе не обеспечивает изоляцию.
Права проверяются backend на основании внутреннего UUID пользователя и
глобальной роли.

Действия записи через приложение (загрузить, править свою карточку,
предложить из Differ, editor) требуют аккаунта. Гость на стартовом графе
открывает **опубликованную общую** карточку (§5.6 / ТЗ 2.64). GraphNotes
**не отдаёт** опубликованную общую файлами (нет ZIP «Скачать», нет clone
корпуса как UX). Чтение общей — граф и карточки в приложении.

### 3.6. Канон всегда один (ТЗ 3.05)

Ровно один канон. Product editor, technical editor, code writer,
наблюдатели и агенты Codex/Cursor читают одну истину: `PRODUCT_SPEC.md`,
`MASTER_CONTEXT.md`, принятые ADR. Нет второго Markdown-канона, чат не
спецификация, нет личного ТЗ у агента. Если код и ТЗ расходятся —
остановиться. Leftover в runtime — недописанный код, не второй канон.

Движок editor-diff — MediaWiki **wikidiff2** C++ (ТЗ 3.03 / ADR-018).
Native helper в образе backend; `php-cli` / `php-wikidiff2` — не
install path этого helper.
