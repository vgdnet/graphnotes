## 8. Критерии приемки MVP

MVP считается функционально готовым, когда:

- пользователь регистрируется с **обязательной почтой** и входит по
  логину/паролю для вклада через UI (после ТЗ 2.86 / прода — регистрация
  только по ссылке из письма-инвайта, окна «Регистрация» нет, §17;
  до той волны улица открыта);
- на инсталляции **rhizome.vsepsy.ru** учётка vsepsy.ru с почтой и паролем
  входит без второй регистрации; хеш пациента и роли `/ops` не переносятся
  (§6.1.3);
- открытый пароль нигде не хранится;
- в **Настройках** заполняет контакты (телефон и Telegram по желанию),
  пользуется складом у нас и при желании подключает git; принимает/отзывает
  договор автора; создаёт и отзывает токен плагина Obsidian; в кабинете
  снова видит ключ `gnp_…`, чтобы скопировать позже; видит историю
  входов с токеном за ~6 месяцев, не дольше года (кто / IP / какой токен) и блокирует ключ;
  git-форма не на графе;
- **стартовая страница — граф** без входа; гость ищет, видит подсветку и
  открывает опубликованную общую карточку (клик по узлу, `[[wikilink]]`,
  хит поиска): Markdown и локальный граф сбоку; общую на странице не
  правят; свою личную автор может править (§6.5.2);
- GraphNotes не отдаёт опубликованную общую ZIP и не предлагает clone корпуса;
- пользователь загружает `.md`/ZIP на склад GraphNotes, копирует локальный
  граф из Obsidian тем же складом (плагин / API, **бесплатно**, ТЗ 2.82)
  и/или подключает git как коннектор (copy-in); GitHub не обязателен,
  чтобы иметь свой граф;
- передача из плагина **не** публикует в общую, **не** создаёт предложение и
  **не** обходит Differ; чужие личные файлы токену недоступны;
- на сайте ризома смотрит личный склад: автор сам предлагает что хочет;
  ризома может пометить карточки, которых в общей нет, и предложить темы
  (§6.6.3); в общую по-прежнему только Differ и очередь;
- ZIP/MD upload **не** пишется в подключённый git и **не** выгружает общую;
- система индексирует wikilinks, Markdown-ссылки, теги и unresolved links;
- индекс связан с конкретной Git revision;
- пользователь видит граф общей и **свой** личный слой из локального склада;
  в меню слоя — «ваша ризома», не «ваш git»;
  на холсте — **весь граф** и **локальный граф** (глубина, «Показать всё»);
- пользователь видит свой авторский вклад: написанные заметки, введённые связи,
  состояния личное / предложено / принято; пустой Differ не стирает принятое;
- на общей ризоме читатель видит автора принятого узла или связи, когда
  provenance известен;
- пользователь создает предложение из выбранных результатов Differ;
- `#/card/`: user ищет свою и общую; editor — плюс правки очереди; admin —
  все открываемые карточки; слой хита подсвечен;
- editor видит человеческий текстовый diff и graph diff/preview;
- очередь предложений: вкладки Новые / В работе / Отклонённые; сначала текст
  карточек и связи, потом ризома; отклонение и возврат — с комментарием автору;
- editor принимает, отклоняет, возвращает или откатывает с причиной;
- editor/admin не может принять собственное предложение;
- admin открывает «Администрирование» отдельной вкладкой с разделами
  «Пользователи», «Журнал» и «Установка»: ищет и создаёт учётки, назначает
  роли, блокирует, задаёт пароль, сбрасывает сессии; открытый пароль нигде
  не хранится и не пишется в журнал; user и editor эту вкладку не видят;
- журнал значимых действий (в том числе смена пароля admin’ом и передача
  из плагина Obsidian в личное) хранится в **базе** GraphNotes и читается
  admin’ом с фильтрами; пароли и секреты токенов в записи не попадают;
- если SMTP инсталляции задан, регистрация подтверждается письмом, вход —
  пароль к подтверждённой почте **или** письмо с вкладки «Вход»
  (код / `#/auth/login-code?token=`); секреты SMTP не в API;
- после merge общественная ризома переиндексируется до merged revision;
- читатели никогда не видят частично применённое предложение;
- PostgreSQL-индекс может быть восстановлен из локального склада `.md`;
- тела не кладут в базу «чтобы искать быстрее»; выгрузка своей — со склада
  (ТЗ 2.63);
- канонические тела опубликованной общей не живут в PostgreSQL как второй
  корпус в обход Differ;
- ни один graph-файл не используется как параллельный источник истины;
- применимые security, migration, backup и deployment проверки текущих стадий
  выполнены на `rhizome-test` до продвижения на `rhizome`.

## 9. Нефункциональные требования

### 9.1. Безопасность

- все операции проверяют аутентификацию, глобальные назначения, ownership личной
  ризомы и тип слоя;
- секреты не коммитятся и не пишутся в журнал / историю входов / ответы
  плагинного API; исключение канона ТЗ 2.76: владелец в cookie-сессии
  читает **свой** ключ плагина из кабинета, чтобы скопировать в плагин;
- загрузки ограничены и защищены от traversal и архивных бомб: ZIP до
  10 000 файлов (свыше — 400 `archive has too many files`), сжатый архив
  2 МиБ, распаковка 8 МиБ, файл 256 КиБ;
- белый шум в личном ingest (бинарный / высокоэнтропийный `.md`, каша
  из символов) не индексируется: HTTP 400 `content is not Markdown notes`,
  учётка блокируется, admin’ам письмо; уже проиндексированные заметки
  остаются; обычный vault (~120 заметок, fences, YAML, кириллица) проходит;
  путь плагина отклоняет мусор как 415 `unsupported_type` **без** lock;
- webhook GitHub проверяется криптографически;
- GitHub credentials имеют минимально необходимые права;
- deployment Git-доступ на `rhizome` только read-only без push-capable
  credentials;
- backend и PostgreSQL не публикуются в LAN/DMZ без отдельного решения;
- антипарсинг гостевых карточек — **не этот пункт**: §16 / ТЗ 2.80,
  только после прода, не на `rhizome-test`.

### 9.2. Надежность и согласованность

- операции синхронизации имеют наблюдаемый статус и понятную ошибку;
- webhook и фоновые reconciliation-операции идемпотентны;
- при расхождении Git и индекса побеждает каноническое Git/Markdown-состояние;
- миграции проверяются на `rhizome-test` до стабильного окружения;
- PostgreSQL использует сохраняемый volume и проверяемое резервное копирование
  до production hardening.

### 9.3. Наблюдаемость

- process health отделен от database/integration health;
- ошибки синхронизации содержат correlation/context без утечки секретов;
- аудит связывает бизнес-действие с пользователем, ролью, слоем, proposal и Git
  revision и **хранится в базе** GraphNotes; секреты и пароли в записи не
  входят; журнал читает admin.

### 9.4. Рост единой общей ризомы

- Graph API возвращает ограниченный подграф, а не всю базу по умолчанию;
- notes, links, revisions и proposals имеют подходящие PostgreSQL indexes;
- re-index поддерживает affected-set/incremental path и проверяемый full rebuild;
- proposal/history lists используют pagination и retention/archival policy;
- опубликованная shared revision переключается только после полной готовности;
- новые инфраструктурные компоненты добавляются только по измеренным данным;
- нагрузочные baseline фиксируются на Stage 5, 8 и 9.
