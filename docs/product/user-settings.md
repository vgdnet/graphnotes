## 5.5. Настройки учётной записи

Экран **«Настройки»** — **`/user`** (ТЗ 2.58). Место, где человек правит
себя, а не ризому. Не граф, не Differ, не «Администрирование», не публичная
карточка человека. Холст — `/graph` (ризома по умолчанию; ТЗ 3.00); стартовая
карточка — `/card` (§5.6). Основной личный склад — **у нас**. Пишет **плагин**.
На `#/user` **нет** вкладки «Свой git» и нет формы связать личный git
(ТЗ **3.38**). Git copy-in — leftover API, не кабинет.

В шапке **нет** отдельных кнопок «Настройки» и «Выйти». Когда человек вошёл,
в шапке видно **под кем залогинен** (отображаемое имя). Нажатие на это имя
открывает **`/user`**. Имя и «Войти» не прижаты к рамке окна — у шапки тот
же боковой отступ, что у логотипа. «Выйти» — **внизу** экрана настроек.

В настройках **четыре** блока на одной странице (вкладки одного экрана):

1. **Личные данные**
2. **Договор автора**
3. **Obsidian** — персональные токены плагина (ТЗ 2.68–2.76)
4. **Пригласить пользователя** — кнопка и форма отправки инвайта (почта → письмо со ссылкой, ТЗ 2.85–2.86). Только здесь, не в «Личных данных».

Карточка пользователя в ризоме — `#/users/{login}` (§5.4 / ТЗ 2.60 / **2.97**).
Настройки — то, что человек заполняет и включает. Это не одно и то же окно.

### 5.5.1. Личные данные

Поля учётки в настройках:

| Поле | Обязательность | Зачем |
| --- | --- | --- |
| Отображаемое имя | да | как зовут на карточке и в очереди |
| **Почта** | **да** | связь с человеком, восстановление, письма; не nullable |
| Телефон | нет | по желанию |
| Telegram | нет | контакт (ник или номер), **не** вход через Telegram |
| Аватар | нет | публичная карточка, по желанию |
| Ссылки (сайт, соцсети) | нет | публичная карточка, по желанию |

- Почта уникальна в инсталляции. Без почты регистрация не завершается и
  статус автора не включается.
- Телефон и Telegram не нужны, чтобы читать общую или принять договор.
- Телефон и Telegram **по умолчанию не публичны**. На карточке автора
  видны только если человек явно включил показ. Admin видит служебные
  контакты на «Пользователи».
- Telegram как **вход** (OAuth / бот-identity) по-прежнему вне текущего
  password-login (ADR-002, §6.1). Поле в настройках — только контакт.
- Вход по почте со своего SMTP — §6.1.2: если SMTP задан, регистрация
  **не открывает сессию**, пока письмо со **ссылкой** `#/auth/confirm?token=`
  (и 6-значным кодом) не подтверждено; дальше почта — идентификатор входа
  (код/ссылка или пароль). На «Вход» при SMTP есть «Войти письмом»
  (логин или почта → письмо на ящик учётки → код или
  `#/auth/login-code?token=`). Тот же контур даёт **сброс пароля**
  («забыли пароль»): код и ссылка живут **30 минут**; после истечения форма
  снова просит письмо, не оставляя полусессии. Ссылки в письме ведут на
  публичный адрес инсталляции (Admin → Установка), не на LAN. Обязательная
  почта **уже** есть как данные учётки.
- На **rhizome.vsepsy.ru** та же почта и пароль, что на vsepsy.ru, — вход
  без второй регистрации (§6.1.3). Telegram по-прежнему не вход в ризому.
- Строка «Приглашен … от @user» (кто позвал **вас**) остаётся в этом
  блоке. Кнопки и формы **отправить** приглашение здесь нет — §5.5.9.

### 5.5.2. Свой git (снято с кабинета, ТЗ 3.38)

**Владелец снял поверхность.** На `#/user` нет вкладки «Свой git», нет
фразы «Личный git не связан — можно загрузить .md в локальный склад.»,
нет формы связать / отключить личный GitHub. Рабочая копия знания —
склад GraphNotes; пишет **плагин**. Кнопок загрузки `.md`/ZIP на сайте
нет (ТЗ 2.96) — не возвращать.

Личный git как XOR-коннектор **не канон ingest** (ТЗ **3.35**). Leftover
`POST`/`DELETE /api/personal/connect` и copy-in могут остаться в backend
для операторов; кабинет их не вызывает. Не требовать git для Differ или
вклада в общую.

Исторически (ТЗ 2.62–2.63, снят **3.35**): git копировал `.md` в локальный
склад. Отключить leftover-связь **не стирает** уже скопированные файлы.

### 5.5.3. Договор автора

Каноническое место договора — **настройки**, блок «Договор автора», не
отдельный скрытый URL и не чекбокс только на форме регистрации.

Человек должен суметь:

- прочитать актуальный текст договора;
- принять его checkbox’ом (фиксируются UUID, время, версия текста);
- видеть, принят ли договор, какая версия, когда;
- отозвать статус автора (новые вклады блокируются до повторного принятия;
  опубликованное в общей не вырезается само, §5.4).

Если человек ещё не автор, но жмёт «предложить в общую» — продукт
отправляет в этот блок настроек, а не молча создаёт предложение.

Канонический текст договора (версия `2026-09-05`) — только в **Настройках →
Договор автора**. На **О программе** договора нет (ТЗ 2.78, §5.5.8).

Принимая договор, вы несёте ответственность за содержание своих заметок и связанных с ними связей, которые предлагаете в общую ризому.

Вы можете отозвать статус автора. GraphNotes запишет время отзыва; новые предложения, загрузки как вклад и подключение git как вклад будут недоступны, пока вы не примете договор снова. Заметки, уже принятые в общую ризому, остаются в её git.

### 5.5.4. Оформление: светлая и тёмная тема

В продукте две темы — **светлая** и **тёмная** — в том же визуальном языке
GraphNotes (уголь / бумага, мятный акцент, без радужной палитры). Обе должны
быть читаемыми: граф (подписи узлов), Differ, настройки, страница карточки.

- Переключатель на виду: в шапке (в том числе у гостя) и в настройках — **один
  и тот же Theme Switcher**, не четвёртая вкладка и не форма на графе.
- Это **не** две текстовые кнопки «Светлая» / «Тёмная» рядом. Управление —
  компактная скользящая таблетка с иконками солнца и луны: ползунок на
  солнце = светлая, на луне = тёмная. Активный режим читается с первого
  взгляда.
- С клавиатуры — как переключатель (`role="switch"`, `aria-checked` для
  тёмной темы), без ловушки фокуса.
- Выбор хранится в браузере человека (`localStorage`), не в учётки на сервере.
- Если выбора ещё нет — берётся `prefers-color-scheme` системы.
- Подписи на графе берутся из токенов темы, не из бледных захардкоженных
  цветов: на тёмном — светлая буква с тёмным контуром холста, на светлом —
  тёмная буква со светлым контуром. Цвета слоёв (общая / ваша ризома / нет
  заметки) остаются различимыми в обеих темах.

ADR для темы не нужен: это UX без смены семантики знания, ролей или API (§13.2).

### 5.5.5. Что не класть в настройки

- очередь предложений и Graph Diff — рабочие экраны editor’а;
- назначение ролей, блокировка, смена чужого пароля и журнал действий —
  «Администрирование», только `admin` (чекбоксы уведомлений на карточке
  учётки — §5.5.6, не журнал и не смена роли);
- тела заметок и история текста — git, не форма профиля;
- список полей «светить всему интернету» — пока открытый вопрос (§6.1.4);
  когда решим, сюда же: включение ачивки / данных для сайта.

### 5.5.6. Уведомления (почта / Telegram)

Каналы доставки на инсталляцию те же: **почта** (SMTP) и **Telegram**
(бот `GRAPHNOTES_TELEGRAM_BOT_TOKEN`, контакт в профиле). Telegram —
канал, **не вход**. Токен бота не коммитится и не отдаётся в API.
Без SMTP / без бота включённое предпочтение хранится, отправка не идёт.
**По умолчанию выключено** — не спамить.

Поля — **Настройки → Личные данные**. Admin может щёлкнуть то же на
карточке учётки в **Администрирование → Пользователи**.

#### Очередь editor’а

`editor` и `admin` видят **два** чекбокса каналов: «новые правки пришли
по ризоме» — почта и Telegram по отдельности. Обычный `user` эту пару
не видит.

#### Изменения в карточках, которые вы правили (ТЗ 3.14 / **3.15**)

Любой автор (роль `user` и выше, договор принят) видит **одну**
настройку — галочка **или** ползунок, подпись ровно:

**«Получать уведомления об изменениях в карточках, которые вы правили»**

Не два чекбокса «почта / Telegram» и не вторая пара как у очереди.
Включил — письмо (если SMTP) и Telegram (если бот и контакт). Выключил —
только список во вкладке Сверка.

Когда в карточках, которые он уже отдавал в общую, появилась чужая
принятая правка (входящий Differ, §6.6.5): какая карточка, ссылка на
**Сверку** `#/differ`. Один раз на появление входящей строки.

Это не лента, не follow чужих карточек и не Telegram-вход. Подписка
автоматическая на пути из его принятых предложений. Mute по одной
карточке в этой волне нет.

### 5.5.7. Токены плагина Obsidian

Плагин **GraphNotes Publisher** (ТЗ 2.69–2.76 / **2.82**, каталог продукта
`obsidian-plugin/`) копирует локальный граф **только в личное хранилище**
этого аккаунта (§6.3.4). Это **бесплатно** (не тариф Publish). Тот же склад,
что локальный склад (кнопок загрузки `.md` на сайте нет, ТЗ 2.96; in-app
правка выключена, ТЗ 2.93). Когда писать — настройка плагина
(ТЗ **2.90**): кнопка **«Передать правки на сервер»** в виде боковой
панели Obsidian (как Source Control у Git); иконка на ленте тоже пишет;
закрытие файла, минуты после правки или интервал. Не на каждый символ.
Общую ризому, предложения и Differ плагин не создаёт и не обходит: разговор о вкладе —
на сайте (§6.6.3).

Токен — простой личный ключ API `gnp_…` (`token_urlsafe(32)`, ТЗ 2.70 /
2.72 / **2.76**). Канон: ключ **хранится у нас** во вкладке **Obsidian**
и **снова показывается**, чтобы скопировать позже. Тот же ключ копируют
в GraphNotes Publisher (тот же ключ копируют в leftover Card Merge,
пока один пакет не поставлен; ТЗ **3.26** снимает 3.09: канон — один
плагин; очередь `/queue` у `editor` / `admin` без тел; «Принять в работу»
+ две операции 3.25; sync `.md` как у участника плюс очередь; авторский
Differ в плагине нет; `personal:read`). Каждый leftover-пакет запоминает
ключ в своём `data.json`:
после перезапуска Obsidian вставлять снова не нужно. Это не «секрет один раз», не аналог SSH-ключа и не модель
«на сервере только хеш». SHA-256 рядом нужен серверу, чтобы найти
Bearer, не вместо ключа в кабинете и не «крепость».
Поставлено в ТЗ 2.79 (Alembic `0018`–`0019`).

Безопасность: чужой вход — **отозвать ключ** здесь же; плагин
с отозванным ключом писать не сможет. Когда доступ восстановили —
создать новый ключ в кабинете и снова скопировать в плагин. Пароль
учётки в плагин не вводится.

- Токен создаётся и отзывается во вкладке **Obsidian** экрана `/user`.
  Пароль учётки в плагин не вводится.
- Права токена ограничены: чтение/запись личного склада; удаление — отдельный
  scope, по умолчанию выключен.
- Срок по умолчанию 30 дней, максимум 90. Отзыв и истечение останавливают
  ещё не зафиксированную передачу.
- Запись в личное требует активный договор автора, как у leftover
  загрузки `.md`. Leftover git-коннектор в API **не** выключает запись
  плагина: рабочая копия всегда локальный склад (ТЗ 2.62 / **3.38**).
- **История входов (ТЗ 2.73–2.74):** на той же вкладке видно, кто
  заходил, откуда (IP, User-Agent) и каким токеном (имя и отпечаток).
  Сам ключ в истории нет. Чужой адрес — человек отзывает токен здесь
  же. Отзыв не стирает историю. В **рабочей** базе строки живут около
  полугода (по умолчанию ~183 дня), не дольше года — чтобы не забить
  склад. Вечный архив и отдельная база логов — следующая архитектура,
  не эта волна.

### 5.5.8. О программе

Подвал прижат к низу страницы — кнопка **«О программе»**, без строки лицензий («Карточки — WTFPL.
Программа — AGPL-3.0.»). Экран **`#/about`** (гость и вошедший) показывает
текст ризомы (ТЗ **3.36**):

Ризома психоанализа — совместная база знаний по психоанализу: школы, авторы, понятия, тексты, клинические идеи, библиография, маршруты чтения и связи между ними.

Карточки соединены в общий граф — ризому, по которой можно двигаться от узла к узлу. База никогда не будет закончена и бесконечно обновляется: каждый автор ведёт свой слой заметок и предлагает их в общую ризому.

Главный редактор ризомы — Мария Надршина; обновления — https://t.me/unconsciousjourney.

Вкладка браузера и og-теги шаринга: название **«Ризома психоанализа»** и это же короткое описание. Картинки превью в этой волне нет.

### 5.5.9. Пригласить пользователя

Четвёртый блок экрана `/user` — вкладка **«Пригласить пользователя»**
(ТЗ 2.85–2.86, размещение на отдельной вкладке; после снятия «Свой git»
в **3.38** — не пятый). Сюда убраны кнопка
«Отправить приглашение», поле почты, статус отправки и список ещё не
принятых писем. В «Личных данных» этой формы нет.

Любой вошедший указывает почту; сервер шлёт ссылку
`#/auth/invite?token=` на публичный URL инсталляции. Без SMTP письмо
не уходит. Улица не регистрируется. API тот же: `POST /api/invites`,
`GET /api/invites`. RBAC не меняется: инвайт может выдать любой
активный с учёткой.
