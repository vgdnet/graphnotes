## 6. Функциональные требования MVP

### 6.1. Аутентификация

- GraphNotes использует собственную регистрацию и login/password;
- внутренний идентификатор пользователя - UUID;
- открытый пароль не хранится и не логируется;
- хранится только стойкий `password_hash`;
- поддерживаются login, logout, текущий пользователь и безопасный механизм
  продолжения сессии;
- пользователь может быть заблокирован без удаления данных;
- `admin` может задать новый пароль любой учётке (§5.3.1); открытый пароль
  при этом не читается, не хранится и не пишется в журнал;
- регистрация всегда создаёт `user` и не позволяет самостоятельно получить
  `editor` или `admin`;
- **ТЗ 2.86 / §17 (поставлено 2.89 на `rhizome-test`):** новая учётка
  только по **ссылке из письма-инвайта**; вкладки «Регистрация» нет;
  инвайт может выдать любой с учёткой (порог «10 карточек» снят, 2.85).
  `POST /api/auth/register` отвечает 410;
- **почта обязательна** при регистрации и дальше хранится у учётки;
  без почты аккаунт не считается завершённым;
- телефон и Telegram — необязательные контакты в настройках (§5.5.1), не вход;
- Telegram как identity provider остается будущим optional, привязанным к
  существующему UUID, и не входит в текущий MVP password-login;
- подключение git, договор автора и токен плагина Obsidian — экран **Настройки**, не граф (§5.5).

#### 6.1.1. Юридический договор автора и фиксация вклада

- Пользователь принимает юридический договор в **Настройках** (блок
  «Договор автора», §5.5.3, ADR-010). Регистрация без этого блока не
  включает статус автора сама.
- Статус автора используется продуктом для:
  - закрепления ответственности за содержание заметок и связей, которые
    человек предлагает в общую;
  - отзыва и повторного принятия: автор забирает статус автора; новые
    предложения, загрузки как вклад, передача из плагина Obsidian в личное
    хранилище и подключение git как вклад блокируются,
    пока договор не принят снова; уже принятые в общую заметки остаются в
    её git;
  - согласия, что карточки в общую идут по **WTFPL**, а программное
    обеспечение GraphNotes остаётся **AGPL-3.0** (разработчик Юрий Ефимов,
    y@psychoanalyst.pro). Второго LICENSE в репозитории нет.
- Запись кто/когда/версия на учётке остаётся служебной. Видимый текст
  договора — §5.5.3 (версия `2026-09-05`), только в Настройках. На
  **О программе** — титры, не договор (§5.5.8).
- Поля учётки дополнительно: `is_author`, `author_contract_version`,
  `author_contract_accepted_at`, `author_contract_withdrawn_at`.

#### 6.1.2. Авторизация через почту (SMTP инсталляции)

Вход и регистрация **через почтовый ящик** идут с **своего домена и своего
почтового сервера** инсталляции, не через Google / GitHub / Telegram OAuth
(ADR-017).

- почта — уникальный идентификатор входа, привязанный к тому же UUID; вход
  паролем принимает логин **или** почту;
- если заданы `GRAPHNOTES_SMTP_HOST` и `GRAPHNOTES_SMTP_FROM`, регистрация
  **не открывает сессию**, пока почта не подтверждена: сразу уходит письмо
  с **ссылкой** `#/auth/confirm?token=` и одноразовым 6-значным кодом
  (тот же контур `POST /api/auth/email/request` /
  `POST /api/auth/email/verify`). Письмо не может быть только кодом —
  ссылка обязательна. Сессия открывается после перехода по ссылке или
  ввода кода. Пароль к неподтверждённой почте не входит;
- **публичный адрес сайта** в письмах (подтверждение, вход кодом, сброс
  пароля, уведомление очереди) — один на инсталляцию, вида
  `https://rhizome.vsepsy.ru/#/auth/confirm?token=`. Правится в Admin →
  **Установка** и сохраняется в базе (переживает пересборку Compose).
  `GRAPHNOTES_PUBLIC_BASE_URL` — начальное значение; по умолчанию
  `https://rhizome.vsepsy.ru`. Не второй домен продукта;
- **одноразовый код и ссылка живут 30 минут**. По истечении сессия не
  открывается и новый пароль не ставится; cookie сброса чистятся; форма
  сброса снова просит письмо. Повторная отправка на существующую почту
  реально уходит; ответ всегда один и тот же (нельзя понять, есть ли
  адрес). Повтор не чаще чем раз в 60 секунд, пока код ещё жив;
- вход при рабочем SMTP: письмо со ссылкой/кодом **или** пароль к уже
  подтверждённой почте. На вкладке «Вход» (ТЗ 2.81) человек выбирает
  «Войти письмом»: запрос принимает логин или почту, письмо только на
  ящик учётки, затем код или ссылка `#/auth/login-code?token=`. Это не
  четвёртая вкладка и не отдельный контур;
- **один экран аккаунта** (как на обычном сайте): «Вход» / «Регистрация» /
  «Не помню пароль» — одна оболочка, не разрозненные модалки. Подтверждение
  почты после регистрации остаётся в том же контуре (код или ссылка).
  **ТЗ 2.86 / §17:** вкладки «Регистрация» нет: новая
  учётка только по ссылке из письма-инвайта;
- **сброс пароля** (забыли пароль **или** логин): запрос принимает **логин
  или почту**. Письмо всегда уходит на **почту учётки** (ящик в профиле).
  Набранный адрес получает письмо только если это почта этой учётки;
  по логину письмо идёт на хранимую почту, не на случайный ввод. Ответ
  всегда один и тот же (нет перечисления учеток). Тот же одноразовый код
  и ссылка, что у подтверждения/входа; человек задаёт **новый** пароль.
  Это не замена смены пароля admin’ом (§5.3.1). Без SMTP запрос отвечает 503;
- исходящая почта — SMTP инсталляции (канон оператора: порт **587 STARTTLS**).
  IMAP (в т.ч. 993) для отправки не используется;
- без рабочего SMTP этот контур не обещается: регистрация сразу открывает
  сессию, почта считается подтверждённой, запрос кода отвечает 503;
- секреты почтового сервера не коммитятся и не отдаются в API; в журнале
  нет открытого пароля, кода и token;
- самоназначение `editor`/`admin` по-прежнему запрещено;
- Telegram как **вход** и сторонние OAuth по-прежнему вне этой версии;
  Telegram как **канал уведомлений** (очередь и изменения в карточке,
  §5.5.6 / §6.6.5 / §6.7), не IdP;
- общая cookie / вход учёткой vsepsy.ru (§6.1.3) этим пунктом не делается.

#### 6.1.3. Учётка с vsepsy.ru

На инсталляции **rhizome.vsepsy.ru** человек с vsepsy.ru входит **той же
почтой и паролем**. Не вторая регистрация, не каталог психологов внутри
ризомы, не Telegram-вход. Полный текст: [vsepsy-identity.md](vsepsy-identity.md).
Ачивка (граф / счётчики / данные для сайта) — §6.1.4; состав полей всему
интернету открыт. Нужен ADR к ADR-002.

Минимальная модель пользователя:

| Поле | Назначение |
| --- | --- |

| `username` | Уникальный логин |
| `password_hash` | Стойкий хеш пароля |

### 6.2. Одна общая ризома; хранение у инсталляции

Продуктово основное хранилище знания — **у GraphNotes**, не GitHub
(ТЗ 2.61). Аналог Obsidian Publish: у каждого свой граф, плюс права и
**одна** общая ризома.

- личное и опубликованная общая — **локальные копии** на инсталляции
  (ТЗ 2.63). GitHub — коннектор: копирует `.md` сюда. Dropbox / Google Drive
  позже, §10. Не два живых склада;
- у каждого пользователя свой личный слой; холст один — `/graph`
  (по умолчанию ризома; ТЗ 3.00);
- общая — ровно одна опубликованная ризома на инсталляцию; чтение только в
  приложении; в общую — Differ и очередь editor’ов;
- GitHub knowledge repo не продуктовый способ забрать корпус (нет clone/ZIP
  в UX) и не «ваш диск»;
- backend может тянуть/пушить от имени приложения при merge leftover;
  App credentials пользователю не выдаются;
- commit SHA в индексе — служебная согласованность, не UX;
- недоступность внешнего git отражается статусом синхронизации, личный склад
  у нас от этого не обязан падать.

### 6.3. Общая ризома не скачивается; одно личное хранилище

GraphNotes **не отдаёт** опубликованную общую файлами: нет ссылки «Скачать»,
нет ZIP архива общей, нет clone корпуса как пользовательского сценария.
Чтение общей — граф, карточка ризомы и Markdown **на чтение** в приложении.

Первичный путь знания **в** общую — Differ и очередь editor’ов.

У аккаунта **ровно одно** личное **рабочее** хранилище: локальный склад
GraphNotes. Это не «git или наши файлы как два канона».

**Как попадают `.md` (ТЗ 2.62–2.63):**

1. Человек пишет / грузит **у нас** — файл сразу в локальном складе.
2. Коннектор (git сейчас; позже Dropbox, Google Drive) **копирует** файлы
   пользователя в тот же склад. Differ, граф и карточки читают копию у нас.
3. GitHub **общей** ризомы тоже только источник: копирует опубликованные
   `.md` в локальный склад общей. Карточки и индекс читают эту копию.
4. Одновременно один активный личный коннектор. Не сливаем Dropbox+git в
   один слой без отдельного решения. Загрузка `.md`/ZIP — тоже копирование
   в личный склад.

**Плагин Obsidian** — бесплатный вход **в тот же** личный склад (локальный
граф через наше API), не второй канон и не публикация (§6.3.4 / ТЗ 2.82).

**Лимит ZIP (ТЗ 2.65).** Один архив в `POST /api/personal/import-md`
принимает до **10 000 файлов** (записи ZIP: vault Obsidian и дамп
личного git — тысячи заметок). Архив из ~120 файлов проходит. Свыше
капа — HTTP 400, текст ошибки **`archive has too many files`**. Сжатый
ZIP по-прежнему до **2 МиБ**, распакованный до **8 МиБ**, один файл до
**256 КиБ**. Защита от zip-бомбы не снимается: коэффициент сжатия,
symlink / special files, шифрование, непринятая компрессия, traversal.

**Белый шум (ТЗ 2.67).** Индексатор нельзя кормить мусором. Любой личный
вход в Markdown-индекс от пользователя — ZIP, один `.md`, in-app
сохранение своей карточки, copy-in из личного git — проверяется на
**белый шум** (мусор, не заметки). Сигналы **сочетаются**, один слабый
не блокирует:

- файл `.md` не UTF-8 или в основном бинарный (в т.ч. нулевые байты);
- очень высокая энтропия Шеннона (случайные байты / «белый шум»);
- почти нет букв (включая кириллицу и CJK) против символов, или каша
  из управляющих символов.

Не блокируют: обычный Markdown, code fences, YAML frontmatter, CJK /
кириллица, короткие заготовки, wikilinks. Лимиты размера и zip-бомбы
(ТЗ 2.65) остаются отдельно: это про объём, не про содержимое.

При детекции: загрузка **отклоняется** (HTTP 400,
`content is not Markdown notes`), мусор **не пишется в склад и не
индексируется**. Учётка **блокируется** тем же `is_active=false`, что
admin lock (сессии снимаются). В журнал — `ingest.white_noise_lock`
(кто, пути, сигналы). Уже проиндексированные настоящие заметки **не
удаляются** — в карантин только эта загрузка. Последний активный admin
не блокируется (инвариант admin lock); ingest всё равно отвергается.

Письмо **всем активным admin** с подтверждённой почтой (или с
включённым notify-on) — SMTP инсталляции (`GRAPHNOTES_SMTP_FROM`,
публичный URL из Admin → Установка). Тема/тело: кто, когда, почему
(белый шум), что учётка заблокирована. Если SMTP выключен или письмо
не ушло — lock и журнал всё равно; сбой почты **не** откатывает
блокировку.

Исторический XOR «git **вместо** склада» снят: git не подменяет склад.
Карточки, Differ и индекс общей читают локальные копии. Leftover vs 2.63:
merge/rollback через GitHub App и живое чтение ветки предложения.

Отключить коннектор **не** значит стереть уже скопированные файлы: копии
остаются в локальном складе.

Обратной записи из GraphNotes в Dropbox / Drive в этой волне нет. Запись
in-app в подключённый git — leftover, пока правки не остаются только у нас.

Загрузка **не** пишет в общую и **не** требует GitHub. В общую — Differ.

GraphNotes **не** записывает выбранные общие заметки в личный слой
(исторический `take-from-shared` снят; ZIP-download общей снят).

Загрузка и in-app — не редактор «как Obsidian» и не второй канон
опубликованной общей. После принятия editor’ом канон принятых путей — **общая
ризома** (локальная рабочая копия). GitHub для общей — источник: копирует
`.md` сюда. Differ остаётся шлюзом записи в опубликованную общую.

- рабочие тела **опубликованной** общей хранятся локально (`shared_notes`)
  после copy-in; это не обход Differ и не тела в `note_index` «для поиска».

#### 6.3.1. Где история загрузок

История «что человек принёс файлом» — **в GraphNotes**. Это не git
пользователя и не git log общей. Загрузка `.md`/ZIP, in-app и плагин
пишут в тот же склад и при подключённом git (ТЗ 2.62).

На каждое событие загрузки продукт хранит как минимум: UUID автора, время,
имена/пути файлов, content hash, отличился ли Differ, ушло ли в предложение
и чем кончилось (принято / отклонено / возвращено). Это та же природа, что
лента взаимодействий: **кто / когда / какой файл**, не журнал набора текста.

Неопубликованный текст загрузки живёт в **серверном личном хранилище**
этого UUID (на стороне GraphNotes), пока его не приняли в общую или автор
не убрал. Это не опубликованная ризома и не «ваш git». Пользователь git не
видит и не обязан иметь. Продуктово это **личный слой** на графе.

Повторная загрузка того же пути — новая запись в истории загрузок и новый
вход для Differ, не last-write-wins в общей.

#### 6.3.2. Как личный слой выглядит на графе

Личный слой на графе общей в меню «Слой», легенде и подписи узла имеет два
имени, не «ваш git». Слои всегда из **локального склада** GraphNotes
(ТЗ 2.62). Коннектор только обновил копию.

- **«ваша часть ризомы»** — пересечение с общей: тот же bounded overlay
  (видимая страница общей плюс только личные заметки, которые сами
  ссылаются на видимые общие узлы). Это не весь личный склад.
- **«ваша личная ризома»** — полный проиндексированный личный граф
  (`GET /api/graph/personal`), когда UI его показывает.
- Состав обоих слоёв **считается автоматически** из склада и индекса
  (wikilink в общую vs всё дерево). Человек не составляет каталог
  «эти заметки — часть, эти — личная ризома».
- Карточки и база изменений (лента взаимодействий / Graph Diff) читают
  ту же видимость слоя, не второй ручной список.

Гость чужой личный слой не видит. Вошедший видит только **свой** overlay
поверх общей и **свой** полный личный граф из локального склада (§6.3).

После уровня доступа к чужому закрытому срезу открывается вид «ризома
автора» — граф и карточки помеченных путей того же личного склада автора.
Не второй индекс, не второй Differ, не ZIP/clone. «Загрузить» здесь =
открыть вид в GraphNotes.

Публичный поиск и комментарии — на опубликованной общей (и на своём слое
себе). Чужой открытый личный как каталог для всех — не требование (§12 п. 9).

#### 6.3.3. Поиск в индексе, выгрузка со склада (ТЗ 2.63)

Склад у нас (2.61–2.63) — рабочие копии `.md` на инсталляции. Это **не**
значит «положить тела в `note_index`, чтобы быстрее искать».

- **Поиск** (`/search`, подсветка на `/graph`) читает производный
  `note_index`. Тела заметок в индекс не кладут «чтобы быстрее искать».
  Elasticsearch — **только после первой утверждённой выкатки на
  production `rhizome`** (ADR-015 / ТЗ 2.83 / §6.5.3); тот же принцип:
  индекс, не второй корпус. До тех пор поиск — SQL.
- **Выгрузка своей** части (если продукт её даст) собирает `.md` со
  **склада** этого UUID (те же байты, что пишет редактор / загрузка /
  коннектор / плагин Obsidian). Не синтез из `note_index`.
- Склад и индекс — разные вещи: `personal_uploads` и `shared_notes` =
  байты `.md`; `note_index` = поиск и граф.
- **Общую** файлами не отдаём (§6.3). GitHub общей — источник copy-in.

#### 6.3.4. Плагин Obsidian → то же личное хранилище (ТЗ 2.68–2.76 / 2.82)

Это **бесплатная** часть публикатора (ТЗ **2.82**): человек пользуется
нашим API, чтобы разместить **свой локальный граф** в личном хранилище
инсталляции. Это не тариф Obsidian Publish и не платная подписка на хостинг
заметок. Плата в продукте, если появится, относится к **уровню доступа /
закрытому срезу** (§5.4.1), не к копированию vault → личное.

GraphNotes даёт **серверный API** и **desktop-плагин GraphNotes Publisher**
(каталог `obsidian-plugin/` в этом продукте, ТЗ 2.69), чтобы правки из
vault Obsidian попали **в единственное личное хранилище** этого UUID.
Это тот же склад, что загрузка `.md`/ZIP и in-app правка своей карточки
(ТЗ 2.62). Не второй vault на сервере, не workspace, не вторая ризома,
не публикация в общую.

**Что человек получает**

- В Настройках (`/user`, вкладка **Obsidian**, §5.5.7) создаёт простой
  личный ключ API `gnp_…` (`token_urlsafe(32)`). Кабинет **хранит и
  снова показывает** ключ, чтобы скопировать позже (ТЗ 2.70 / 2.72 /
  **2.76**). Пароль учётки в плагин не вводится. Чужой вход — отзыв
  ключа; доступ вернули — новый ключ снова из кабинета в плагин.
  История входов ~6 месяцев, не дольше года (ТЗ 2.73–2.74). Вечный лог
  в рабочей базе не копим; отдельная база логов — позже.
- Плагин ставится в vault как сторонний desktop-плагин (Obsidian 1.8.7+).
  В настройках плагина — адрес сервера (без `/api`) и токен; тот же
  ключ плагин помнит в `data.json` (перезапуск без повторной вставки).
  «Проверить подключение». Для тестового HTTP (`rhizome-test`) HTTP
  разрешается отдельно; прод — HTTPS.
- Правки в vault **сами** копируются в личное хранилище после сохранения
  (без выбора карточек и без экрана «что отправить»). Первая заливка
  уже существующего vault — команда «Отправить всё». Совпавшие байты
  не передаются. Одновременно одна операция передачи.
- После успешной передачи те же пути видны как личные карточки, в
  `/graph` (фильтр личного слоя) и в поиске личного слоя. В общую ризому материал **не**
  попадает само. Что отдать в общую — человек решает **на сайте**
  (`#/differ`, §6.6.3) **или** в боковой панели плагина после копии
  в личное (ТЗ **3.20** / **3.27**): список Differ и «Предложить в ризому»
  **сегодня** при `can_propose_to_rhizome` (грубый шлюз роли `user`).
  У `editor` / `admin` панели нет (ТЗ 3.27 сегодня; формула «учётка и
  есть ризома» снята 3.28 / 3.30). Это не
  «editor никогда не предлагает, навсегда» — дыры §5.6.6. Карточка
  остаётся в личном; создаётся заявка.
  Плагин не пишет `shared_notes`. Снимок
  `obsidian-plugin.backup-before-differ/` — не канон.
- Конфликт (путь уже есть с другой версией): пакет не применяется; человек
  видит серверный Markdown и явно подтверждает замену. Серверного
  `force=true` нет; сервер всё равно проверяет версию.
- Удаление на сервере — если у токена есть право удаления и путь уже
  копировался: удаление в vault уходит в личное. Без этого права локальное
  удаление серверный файл не стирает. Переименование = новый путь + удаление
  старого. Локальные файлы vault плагин сам не правит.
- Обрыв связи: открыть окно снова и «Проверить / продолжить». Состав
  операции и токен в `data.json` сохраняются (ТЗ 2.70 / 2.76). Если байты ещё не загруженного
  файла изменились — отменить план и подготовить заново. Если склад уже
  принял файлы, а индекс ещё нет — это видно отдельно, можно повторить
  индексацию.
- Чужие личные файлы токену недоступны, в том числе если владелец токена —
  `admin`.

**Ограничения этой версии (продукт)**

- Направление Publisher: Obsidian → личное хранилище GraphNotes.
  Обратной подмены **всего** личного vault серверным складом нет (ТЗ 2.93 /
  2.91). **ТЗ 3.30:** для **выданной** карточки плагин **скачивает**
  её в vault, когда открывают Obsidian; это не редактор сайта и не dump
  корпуса. ТЗ **3.25** — другой контур: Card Merge после принятия файла
  делает **две отдельные операции** (не одно «Save & Resolve = POST в
  общую»): (1) всегда записать принятый файл в vault (открытие — эта
  заметка; без записи принятие не закончено); (2) только если локальный
  файл ≠ хранилище ризомы — обновить **тот же** серверный файл общей
  от аккаунта editor’а (vault — клиентская копия; Differ —
  write gate невыданного); если совпадают — пропуск. Runtime: сначала
  vault и открытие; POST `/resolve` — вторая операция, 504 её не откатывает. Это не выгрузка корпуса и не редактор сайта. Мобильный плагин и автослияние с общей —
  не эта версия. Авторский Differ — сайт, вкладка Сверка (`#/differ`,
  ТЗ **3.11**), и тот же исходящий список в Publisher после копии в
  личное (ТЗ **3.20**). В общую по-прежнему только заявка и очередь.
  Очередь editor’а — **capability того же плагина**
  (ТЗ **3.26** / **3.10** / **3.25** / §6.6.4), не сверка
  личного склада автора. UI очереди включают, если API говорит, что у
  учётки есть editor-доступ; иначе очередь выключена. Ручная правка
  editor’а — тот же sync, что у участника. **ТЗ 3.09 снят:** канон —
  один пакет. Каталоги `obsidian-plugin/` и `obsidian-card-merge/` —
  leftover-каталог `obsidian-plugin/`; поставленный клиент —
  `obsidian-card-merge/` (sync участника, офер у `user` по
  `can_propose_to_rhizome`, очередь editor’а по `can_see_queue`). Грант
  очереди по тегам / путям / папкам — ТЗ **3.21** / **3.30** / §6.6.6.
- Форматы: Markdown и вложения PNG, JPEG, GIF, WebP, PDF. Исполняемые и
  произвольные бинарные форматы не принимаются молча.
- Запись требует активный договор автора и активную учётку, как загрузка
  `.md`. Подключённый личный git **не** выключает этот вход: рабочая копия
  всегда локальный склад.
- Мусорный Markdown плагин-API отклоняет; учётку при этом **не** блокирует
  (блокировка белого шума TZ 2.67 остаётся у ZIP / одиночного `.md` /
  in-app / git copy-in).

Маршруты — [api.md](api.md). Схемы, коды ошибок и хранение — техническое ТЗ
(`MASTER_CONTEXT`, `docs/deployment/OBSIDIAN_PLUGIN_API.md`).

### 6.4. Индекс знаний

PostgreSQL хранит производный индекс и состояние приложения, включая как
минимум:

| Сущность | Минимальное назначение |
| --- | --- |
| `note_index` | Заметка, слой, владелец personal-слоя, Git-путь, title, slug, content hash, commit SHA; provenance автора, когда известен |
| `note_links` | Источник, цель или unresolved title, тип и исходное представление ссылки; кто ввёл связь, когда известно |
| `tags`, `note_tags` | Нормализованные теги и отношения |
| `sync_jobs` | Репозиторий/ветка/revision, статус, ошибка и время синхронизации |
| `proposals` | Автор, base/head revisions, статус, решение, причина и audit linkage |
| авторский вклад | Производная история: заметки и связи автора в состояниях личное / предложено / принято / закрыто; без канонических тел |
| статистика пользователя | Вклад UUID: карточки, добавленное, принятое, связи; для editor — решения очереди. Свою видит сам, все — admin |
| история загрузок | События ingest: кто, когда, путь, hash, связь с Differ/предложением |
| токен / передача плагина | Служебные таблицы интеграции; не канон Markdown и не вторая ризома (§6.3.4) |
| закрытый сегмент | Флаг пути в **текущем** личном хранилище (git XOR файлы): не в Differ, не в опубликованной общей; кому видно |
| взаимодействия с общей | Лента событий **по каждой карточке ризомы**: кто создал, кто правил текст, кто добавил/снял какую связь, когда, через какое предложение; без тел Markdown |
| взаимодействия с личной | Та же таблица событий: in-app правка **своей** карточки (`edited` / `linked` / `unlinked`) с владельцем слоя; не попадает в ленту общей карточки того же git-пути |

PostgreSQL не становится вторым источником Markdown и не хранит канонические
тела заметок. Индекс должен быть восстановим из локального склада
(и из git общей, пока backend его держит). Provenance автора — производные
данные индекса и предложений, не отдельный канон текста.

Пересборка индекса атомарна для производных чтений: одна операция
(`POST /index/rebuild`, смена SHA на графе/поиске, webhook/опрос) заново
проецирует **общую и все личные** git-слой в `note_index`. Отдельного
поискового индекса нет — `/search` и Graph API читают ту же таблицу на
текущем `indexed_sha`. Пути, которых нет в текущем дереве, не остаются в
поиске и не открывают тело карточки. Комментарии к снятым путям
удаляются при пересборке; новый комментарий требует, чтобы путь был в
текущем общем дереве или в личном слое зрителя (локальный склад).

Производные данные обязаны различать:

- `shared` — опубликованную полностью индексированную общую revision;
- `personal` — личный слой ровно одного владельца: локальный склад
  GraphNotes (коннектор только копирует `.md` сюда, ТЗ 2.62);
- `proposal` — неопубликованный preview конкретных base/head revisions.

Proposed nodes, links, tags и properties не становятся shared до принятия и
завершения индексации merged revision.

#### 6.4.1. Карточка ризомы и статистика изменений

Каждая опубликованная заметка общей — **карточка ризомы** (карточка слова /
понятия). Это тот же узел графа, не вторая сущность.

На карточке пользователь видит:

- текущий Markdown **на чтение**;
- кто создал карточку и когда (принятие в общую или аудируемый commit);
- какие последующие правки текста вошли в общую (кто, когда, через какое
  предложение);
- какие связи **добавлены или сняты** на этой карточке: кто, когда, с какой
  другой карточкой;
- имя в этой ленте открывает **карточку человека** `#/users/{login}` (ТЗ 2.97)
  (публичные достижения, не личный склад).

Текст версий опубликованной общей — её Markdown (в leftover-стеке backend
может держать git общей). Своя личная — склад у нас XOR git. GraphNotes хранит
ленту взаимодействий, потому что git log не равен «этот UUID поставил эту
связь». Тела **опубликованной общей** в PostgreSQL не кладутся как второй
канон. Тело опубликованной общей открывает и гость (§5.6 / ТЗ 2.64).
Ленту и комментарии — только сессия с правом на этот узел. Закрытый срез —
автор, UUID с уровнем доступа, admin.

In-app правка своей личной карточки пишет в ту же ленту (`edited`, при смене
wikilink — `linked` / `unlinked`) с владельцем личного слоя. Лента общей
карточки того же пути эти события не показывает.

### 6.5. Graph API и визуализация

Первая волна — граф **общей** ризомы. Личный overlay — как **личный слой**
этого человека связан с общей: из его git или из серверного хранилища
(§6.3.2). Следующая волна дополняет граф **автором**: чьи это заметки и связи,
не подменяя общую ризому личным vault.

Stage 5 поставляет производный индекс и ограниченный Graph API. Stage 6
добавляет Cytoscape и overlay. MVP должен предоставлять:

- **холст `/graph`** общей ризомы **без логина**: только опубликованный
  публичный слой; поиск подсвечивает узлы; клик по узлу и `[[wikilink]]`
  открывают карточку опубликованной общей (§5.6, §6.5.2 / ТЗ 2.64).
  `/` → `/graph` (по умолчанию граф ризомы; ТЗ 3.00). Вкладки «Мой граф»
  и `/my_graph` нет. **`#/invites`** — страница карты инвайтов
  (`http://172.16.13.14:8080/#/invites` на тесте); JSON
  `GET /api/graph/invites` не в hash; для создателей: у кого сколько
  связей; Code Writer выкладывает на `rhizome-test` (ТЗ 2.98);
- страница карточки — отрисованный Markdown и локальный граф сбоку;
  гость читает опубликованную общую; личное и очередь — после входа;
  `/search` ищет видимый корпус роли (гость — общая; user — своя+общая;
  editor — плюс правки очереди; admin — все открываемые) и подсвечивает
  слой хита (§6.5.2); `/card` без пути — стартовая карточка из настроек
  admin (404, если не задана);
- overlay **вашей части ризомы** поверх общей (сессия): из git, если подключён;
  иначе из серверного хранилища. В меню слоя и легенде — «ваша часть ризомы»,
  не «ваш git»; полный личный граф — отдельно, «ваша личная ризома» (§6.3.2);
- Differ как список односторонних отличий (Stage 7) и Graph Diff (Stage 8);
- узлы заметок и направленные связи;
- открытие исходного Markdown на **странице карточки**: отрисованный
  синтаксис (заголовки, списки, ссылки, `[[wikilinks]]`), не сырой дамп.
  Карточка сначала на чтение. In-app правка — только **своей** личной после
  кнопки «Отредактировать карточку» (§6.5.2). Без права кнопки нет. Общую
  на странице не правят (Предложения / Differ → очередь). Страница не пишет «правок нет,
  авторство только во внешнем git»;
- базовые фильтры;
- различимое отображение unresolved links;
- обработку пустого, изолированного и частично разрешенного графа;
- получение ограниченного подграфа без обязательной передачи всей базы при
  больших объемах.

Следующая продуктовая волна (после первой версии) дополнительно:

- на общей ризоме различимо, кто внёс узел или связь, когда provenance известен;
- вошедший автор может сфокусировать «мой вклад» (свои заметки и связи) поверх
  общей, не вместо общей;
- overlay личного git остаётся слоем именно этого автора;
- поиск по ризоме на Elasticsearch (ADR-015) — **только после первой
  утверждённой выкатки на production `rhizome`**; вопросы §6.5.3
  закрываются в той волне, не сейчас. До тех пор `/search` — SQL.

Визуализация реализуется на React + TypeScript с Cytoscape.js, если новый ADR не
изменит это решение. Подписи узлов и рёбер на графе и Graph Diff читаются в
обеих темах оформления (§5.5.4): цвет буквы и контура — из токенов темы, не
из размытого белого на заливке узла.

Не требуется в текущем срезе: preview набора как в Obsidian, autocomplete
`[[ ]]`, панель backlinks. Тонкий in-app редактор — **своя** личная карточка
(§6.5.2), не общая и не замена vault.

Ориентир жеста графа — демо Cytoscape fCoSE gene: клик по узлу открывает
страницу карточки (§6.5.2). То же демо задаёт **раскладку и вид**
холста (§6.5.1): живая силовая fCoSE, не встроенный `cose`.

#### 6.5.1. Граф как отображение ризомы

Граф — основной вид **общей** ризомы на **`/graph`**, не декорация и не клон редактора Obsidian.
Ориентир по ощущению и управлению — **граф Obsidian**: заметки как узлы, ссылки
как рёбра, живая раскладка, глобальный и локальный виды.

На графе текст не пишут. Связи не создают и не правят перетаскиванием: они из
Markdown. Свою личную карточку автор открывает на чтение и правит после
«Отредактировать карточку» (§6.5.2).

**Гость и сессия:** клик по узлу, который можно показать, **открывает
карточку** (`/card/{путь}`): Markdown и **локальный граф сбоку**.
`[[wikilink]]` на карточке ведёт на другую карточку так же. Узел без права —
замок, не тело. Перетаскивание узла карточку не открывает.

**Два вида, как в Obsidian**

- **Весь граф** — опубликованная общая ризома (при большом объёме — ограниченный
  подграф, не «вся база сразу»).
- **Локальный граф** — выбранная заметка и её окружение на заданную глубину
  (соседи, соседи соседей). Это вид той же общей ризомы, не отдельный vault
  и не замена Obsidian.

Переключение **«весь граф» / «локальный граф»**, **глубина** 1–4 и возврат
**«Показать всё»** живут на холсте (меню «Вид», глубина, кнопка на панели
узла). Без Git-жаргона: не «Соседи» и не «вся страница». Локальный вид
читает тот же Graph API (`center` + `depth`); для узла «вашей части ризомы»,
которого нет в общей, центр — `personal:{путь}`. «К графу» со страницы
карточки открывает **`/graph`** (весь граф) и фокусирует этот узел (своя личная —
слой «ваша личная ризома»).

**Что пользователь делает с графом**

- видит узлы-заметки и связи (обычные — haystack, особые — направленные);
- масштабирует, двигает холст, вписывает граф в экран;
- перетаскивает узел; раскладка **живая силовая fCoSE** (Cytoscape.js +
  `cytoscape-fcose`), как в демо [fCoSE gene](https://js.cytoscape.org/demos/fcose-gene/):
  узлы расходятся, подпись по центру узла с обводкой, наведение подсвечивает
  соседей и приглушает остальное. Цвета слоёв GraphNotes (общая / ваша часть
  ризомы / ваша личная ризома / нет заметки) сохраняются. Слайдеры
  GeneCard/UniProt из демо не переносятся.
  Обычные связи — полупрозрачный haystack; overlay / нет заметки / замок
  остаются направленными, чтобы их было видно;
- выбор узла фокусирует его и **открывает страницу карточки** (§6.5.2);
  на карточке справа (на узком экране — ниже) локальный граф этой заметки;
- карточка открывается по нажатию на узел предсказуемо (drag не открывает
  страницу);
- **ищет карточки** по названию (и видимому слою): совпадение на графе
  подсвечивает узел; клик и хит `/search` открывают карточку (гость —
  опубликованную общую);
- фильтрует: все / изолированные / неразрешённые ссылки / **ваша часть
  ризомы** / **ваша личная ризома** / «мой вклад»;
- отличает неразрешённую цель ссылки от существующей заметки;
  вложенный `.md` (в том числе folder-note `GraphNotes/GraphNotes.md` и
  файлы внутри gitlink) — существующая заметка, не красный «нет заметки»;
  `[[GraphNotes]]` резолвится в `GraphNotes/GraphNotes.md` (§6.5.2);
- видит пустой, разреженный и обрезанный граф без «молчаливой пустоты».

**Как отличить слои (не смешивать черновик и общее)**

Цвета и вид узла/ребра отвечают на «где это знание» и «чей вклад», не на
внутренние Git-имена:

- общее (принято);
- ваша часть ризомы (пересечение с общей) и ваша личная ризома (полный
  личный граф): из **его git**, если подключён, иначе из **серверного
  хранилища** — в меню и легенде графа эти два имени, не «ваш git»;
- неразрешённая ссылка;
- при фокусе «мой вклад» — заметки и связи этого автора.

Предложенное, но ещё не принятое, на общем графе читателя не показывается.
Editor видит структурный Graph Diff в очереди, не как вторую ризому.

**Чего граф сознательно не делает**

- не редактор «как Obsidian»: нет preview, автодополнения `[[ ]]`, панели
  backlinks и письма в узле;
- не создаёт связи перетаскиванием;
- не подменяет общую ризому графом чужого или своего vault целиком;
- не требует аналитики ради аналитики (кластеры, centrality) в этом пункте.

Библиотека отображения — Cytoscape.js с раскладкой **fCoSE**, пока нет нового ADR.
Координаты раскладки — только UI, не знание (не `graph.json`).

### 6.6. Differ

Differ — отдельная продуктовая сущность (ADR-009 + ТЗ **3.13**): **сверка
двух складов** (личное хранилище пользователя и опубликованная общая).
Два добровольных действия на одной вкладке **Сверка** (`#/differ`):

1. **В ризому** (ТЗ 3.11): предложить выбранные отличающиеся карточки
   из личного склада в общую.
2. **Из ризомы** (ТЗ 3.13): если автор уже отдавал карточку в общую и
   там появились чужие правки — увидеть это и при желании принять новую
   общую в **своё** хранилище.

Это не экран GitHub, не канон хранения и не merge-редактор.

**ТЗ 3.11.** У автора нет «Differ личного склада» как merge в Obsidian.
Плагин / copy-in по-прежнему пишут **от человека в наш склад**. Склеивать
«общую слева и свою справа» в плагине нечего. Построчный текстовый diff
и принятие **в общую** — очередь editor’а (`/queue`, wikidiff2), не этот
экран. Не CM6, не «Текст сверки», не Save в vault.

**ТЗ 3.13** не отменяет 3.11: обратный поток — не ZIP корпуса и не
исторический `take-from-shared`. Только карточки, которые этот автор
уже публиковал; только сайт `#/differ`; принять = скопировать
опубликованную общую в его личный склад. ADR-009 («только personal →
shared») ждёт поправку владельца.

Вкладка шапки **Сверка** (`#/differ`) — канон снова (снимает ТЗ 3.01
«вкладки нет»). `#/offer` — только **мои заявки**, не сверка складов.
`/card/{путь}` при двух версиях **не** открывает Differ сам (ТЗ 2.56):
стопка, снизу офер «сравнить в Сверке».

В Differ режимы: **по смыслу** (нейросеть — позже, ADR);
**построчно у автора** при выборе путей — ещё не спроектировано, не
изобретать merge-UX.
**Принятие правок редактором** (ТЗ **3.02 / 3.03**, `/queue`): как у
Википедии, движок **wikidiff2** (ADR-018). Таблица «В ризоме» |
«В предложении». Переключателя inline нет. Graph Diff ниже текста.

Входы: **личный слой** — **либо** revision подключённого git, **либо** набор
загруженных `.md`, никогда оба — и **опубликованная** общая revision.
Исходящее направление — **личный слой → общая ризома** (предложить).
Входящее — **опубликованная общая → личный склад** и только для путей,
которые этот автор уже отдавал (§6.6.5).

Git не обязателен: без него Differ идёт по загрузкам. Git подключён —
Differ только по git, загрузки выключены.

**Свежий git, не вчерашний SHA.** Человек пишет в Obsidian и пушит в свой
публичный репозиторий. Когда он открывает Сверку (`#/differ`) и когда создаёт предложение,
GraphNotes **сам** читает текущий HEAD этого git через GitHub App и сравнивает
уже этот снимок с опубликованной общей. Отдельная кнопка «подтянуть» не нужна.
Тот же подхват: webhook `push`, если настроен; иначе фоновый опрос инсталляции
(минуты, не Celery). GraphNotes не держит второй канонический clone личного
Markdown на диске: канон остаётся в git человека, продукт читает его API.

Git-сравнение — по деревьям (blob SHA путей `.md`), не скачиванием каждого
тела «чтобы нарисовать список». Тела читаются при предложении и при индексе
графа.

Differ считается из Markdown личного слоя. Его нельзя материализовать как
`graph.json` или как тела **опубликованной** общей в PostgreSQL.

Исходящее отличие — Markdown-путь, которого нет в общей, либо путь есть
в обеих, содержимое разное, и путь **не** во входящем списке (§6.6.5).
То, что есть только в общей и автор туда **не** отдавал, Differ не
показывает: это уже опубликованное, его читают в приложении, не забирают
ZIP.

Пустой Differ значит: нечего предлагать в общую **и** нет входящих правок
по своим уже опубликованным карточкам. Закрытые пути автора в исходящий
Differ не попадают: их не предлагают в общую.
После принятия editor’ом **его** предложения и успешной индексации общей
эти пути из **исходящего** Differ исчезают. Если позже чужие правки
разведут общую и его личное — путь появится **во входящем** (§6.6.5).

Пользователь отмечает чекбоксами **подмножество** результатов Differ и
создаёт предложение. Нельзя требовать «весь vault» и нельзя делать основным
управлением обязательное текстовое summary вместо списка отличий.

Graph Diff (Stage 8) — структурный вид того же набора (узлы, связи,
unresolved), не вторая модель сравнения. База изменений и карточки
следуют автоматической видимости слоёв «ваша часть ризомы» /
«ваша личная ризома»: нет второго каталога, какие личные заметки куда
входят.

#### 6.6.1. Правила записи в общую ризому

В общую попадают только выбранные пути из Differ, и только после
предложения и очереди editor’ов. Авторский Differ сам ничего не
склеивает (ТЗ 3.11). Прямая запись пользователя в общую, last-write-wins
в PostgreSQL и GitHub Pull Request как UX запрещены.

1. В общую попадают только **выбранные** пути Differ (добавления и обновления
   Markdown). Удаления из общей через Differ в MVP нет.
2. Создание предложения **не меняет** личный склад и не считается «принятием».
   Загрузка тоже не пишет в общую, пока editor не принял. Подключён git —
   загрузки нет.
3. Несколько предложений по одному пути остаются параллельными, пока editor не
   сольёт одно из них. Конфликт виден, его не маскируют.
4. Editor/admin принимает, отклоняет, возвращает или откатывает с причиной.
   Автор не может решить по своему предложению, в том числе admin-автор.
5. Merge — это Git-слияние Markdown, затем переиндекс. Кастомного three-way
   движка и UI ручного merge нет.
6. Читатели видят только полную опубликованную revision: до конца индексации
   старую, после — новую. Частично применённое предложение скрыто.
7. После успешной индексации принятые пути пропадают из Differ этого
   личного слоя.

Очередь, текстовый diff и Graph Diff — инструменты решения по этим правилам,
не отдельная модель слияния.

#### 6.6.2. Авторский вклад и дополнение Differ

Differ не заменяется. Он дополняется смыслом автора.

1. Результат Differ — **неопубликованный вклад этого автора**: что он написал
   и какие связи предлагает относительно опубликованной общей.
2. Graph Diff того же набора показывает узлы и связи автора, не вторую модель
   сравнения.
3. Принятие не стирает автора: пути уходят из Differ, вклад остаётся в общей
   как provenance (заметки и связи, вошедшие через его предложение или
   аудируемый commit editor/admin).
4. Автор видит три состояния: только в личном git; предложено; принято в общую.
5. Канонический текст — Git автора и Git общей. GraphNotes не ведёт второй
   журнал посимвольного набора и не кладёт тела заметок в PostgreSQL.
6. Editor видит не только список файлов, но и какие связи автор предлагает.

Пустой Differ значит: к общей сейчас предлагать нечего. Он не значит, что
у автора нет принятого вклада.

Differ **не архивируется** как таблица отличий на каждый push: это сравнение
на чтение. История вклада пишется в момент предложения и решения editor’а
(лента взаимодействий, §6.4.1).

#### 6.6.3. Разговор о вкладе: кабинет, затем плагин (ТЗ 2.82 / 2.88)

После того как локальный граф лежит у нас в личном складе, **ризома смотрит
это хранилище**. Плагин копирует в личное и может создать заявку из
исходящего Differ (ТЗ **3.20**); в общую **не** пишет.

Differ — источник списка: что в личном отличается от опубликованной общей.
Тот же Differ **сам предлагает** автору карточки, которых в общей **нет**
(личные пути без пары в ризоме): «у нас такой нет — дай её нам, если хочешь».
Это не второй алгоритм и не merge. Тот же список Publisher может
показать после копии в личное (ТЗ **3.20**). Тела в общую — после
предложения и очереди, §6.6 / ADR-009.

Два направления, оба добровольные и оба идут в общую **только** через
предложение и очередь editor’ов. Принудительной записи в общую нет.
Показ просьбы в кабинете или позже в Obsidian **не** создаёт предложение
и **не** пишет в общую.

1. **Он нам.** Автор сам отмечает в исходящем Differ, что хочет отдать в
   общую, и создаёт предложение.
2. **Мы ему.** Differ помечает его личные карточки, которых **нет** в
   опубликованной общей. Пометка — просьба, не принятие. Автор может
   проигнорировать.
3. **Темы.** Ризома может предложить темы, на которые стоит написать
   новую карточку (дыры общей, висячие ссылки, пробелы слоя). Это
   приглашение писать в **личное**, не готовая карточка в общей.
4. **Общая ему (ТЗ 3.13).** Карточку, которую он уже отдавал в ризому,
   кто-то изменил. Сверка уведомляет и предлагает принять новую общую
   в его личное хранилище. Не просьба отдать ещё раз и не ZIP.

**Порядок поставки (ТЗ 2.88 / 3.11 / 3.13 / 3.20).** Список, просьбы и
входящие правки живут **на сайте**, вкладка **Сверка** (`#/differ`):
исходящее — чекбоксы, предложить; входящее — §6.6.5. Publisher после
копии в личное показывает тот же исходящий список и создаёт заявку
(«Предложить в ризому»), **если** `can_propose_to_rhizome` (сегодня роль
`user`, ТЗ **3.27**, грубый шлюз). У editor/admin панель офера скрыта;
очередь остаётся. Не вечный ACL (§5.6.6). Офер на карточке ведёт на сайт, не в merge.
Плагин **не** читает авторский Differ и **не** сливает
пару в vault (снято 3.04–3.07 для автора). Очередь editor’а — тот же
плагин (§6.6.4): UI очереди при открытии Obsidian, если у учётки
editor-доступ. Запись в общую — очередь editor’а: сайт `/queue`
или вторая операция после принятия (обновление хранилища ризомы от
аккаунта editor’а, только если локальный файл ≠ склад; Differ —
gate). Не равнять Save & Resolve с POST в общую (ТЗ **3.25**).
UX тем сверх смысла выше не выдумывать.

#### 6.6.4. Очередь заявок в Obsidian-плагине (ТЗ **3.26** / **3.10** / **3.11** / **3.12** / **3.16** / **3.22** / **3.25** / **3.27**)

У **одного** Obsidian-плагина (канон ТЗ **3.26**) справа — вид «Очередь
правок», если у учётки есть editor-доступ. Это **не** отдельный пакет
«только для editor’а»: отличие editor vs user — очередь предложений
из API (`GET /api/proposals`), показанная при открытии Obsidian.
Нет editor-доступа — UI очереди выключен. Тот же плагин.

**ТЗ 3.26 снимает 3.09.** «Два пакета, не склеивать» больше не канон.
Канон — один клиент: так проще; позже тот же плагин показывает и прячет
возможности по ответу API, когда доступ станет **не ко всем карточкам,
а только к определённым** (стык с ТЗ 3.24). Текущие каталоги
`obsidian-plugin/` — leftover. Поставленный один клиент —
`obsidian-card-merge/`: sync vault ↔ личное; «Предложить в ризому»
только при `can_propose_to_rhizome` (сегодня роль `user`, ТЗ **3.27**,
не навсегда); очередь editor’а по `can_see_queue`. Editor/admin панель
офера не видят и Differ-офер не опрашивают. Весь vault в общую sync
**не** проводнить (дыра среза — §5.6.6).

Editor синхронизирует `.md` vault ↔ склады GraphNotes **тем же sync**,
что участник. Если editor правит карточку вручную — это тот же sync.
Плюс, при editor-доступе, приём в общее через очередь. API режет по
роли, scopes и позже по карточке; ручная раздача второго `.zip` — не
граница безопасности и не канон. Выгрузка всей опубликованной общей
ZIP’ом из плагина — запрещена (ТЗ 2.5 / §6.6.3). Модель двух складов —
[access.md](access.md) §5.6.6. ТЗ 3.22 сужен 3.25: локальная копия
**принятых** карточек законна; dump корпуса и вторая каноническая
общая — нет.

Editor синхронизирует `.md` vault ↔ склады GraphNotes **тем же классом
copy**, что участник, плюс приём из очереди. Dump корпуса и вторая
каноническая общая — нет.

**ТЗ 3.25 — две отдельные операции после принятия файла.**
Не сливать в одно «Save & Resolve = POST в общую». Card Merge —
очередь правок **от других участников**; принятие **через editor’а**.

1. **Всегда после принятия: запись в локальный vault.** Принятый
   файл **обязан** быть записан в vault editor’а по пути карточки.
   Открытие карточки — **эта локальная** заметка (новый лист обычного
   редактора, не MergeView). Если локальная запись не удалась —
   принятие **не закончено**.
2. **Вторая операция, только если отличается: обновление хранилища
   ризомы.** Сравнить записанный локальный файл с файлом в хранилище
   GraphNotes (опубликованная общая). Если отличаются — обновить
   хранилище **от аккаунта editor’а** (у этой учётки есть доступ к
   общей ризоме). Это gated-обновление: Differ / очередь по-прежнему
   write gate в опубликованную общую. Если файлы **одинаковые** —
   вторую операцию **пропускают**.

**Runtime 3.25.** Save & Resolve сначала пишет vault и открывает
локальную заметку. POST `/api/proposals/{id}/resolve` — вторая
операция, только если локальный текст ≠ опубликованная общая;
таймаут/504 не откатывает vault и не блокирует открытие.
Новый HTTP-глагол не выдумывать.

Card Merge **не** «только кэш, никогда заметка vault». Кэш
`.obsidian/plugins/…/work/` — черновик сравнения; принятая карточка —
обычная заметка. Канон опубликованной общей остаётся у GraphNotes;
vault — локальная рабочая копия принятых, не вторая ризома.

**ТЗ 3.10 / 3.11.** Плагин **не** смотрит Differ личного склада.
Список — очередь предложений из API, показанная при открытии Obsidian,
**если** у учётки editor-доступ (`GET /api/proposals`: открытые /
conflicted / failed; та же вкладка **«Новые»**, что сайт `/queue`).
Нет editor-доступа — UI очереди выключен (Differ автора только
`#/differ` на сайте). Пустой список: «Нет новых предложений». Нет
токена — «Введите токен». Иконка очереди открывает панель.

**ТЗ 3.12.** Панель показывает **только очередь** (метаданные заявок).
Тела карточек при открытии и «Обновить» **не** качаются — иначе всё
тормозит. Кнопка **«Принять в работу»** один раз скачивает **две**
стороны этой карточки (`before` = опубликованная общая, `body` =
предложение) через `GET /api/proposals/{id}/files/{path}` и кладёт их
в локальный кэш плагина (каталог плагина в `.obsidian` — черновик
сравнения, не принятая заметка). Слияние открывается с диска, без сети.
**Save & Resolve** в UX — принятие **этой одной** карточки (ТЗ **3.18**):
только тот путь, который editor правил; остальные файлы той же заявки
остаются в очереди (`GET /api/proposals`, вкладка «Новые»). Не
принимать всю заявку из плагина. Не равнять Save & Resolve с
`POST /api/proposals/{id}/resolve`. **ТЗ 3.25:** две операции
(локальная запись всегда; обновление хранилища ризомы только если
локальный файл ≠ склад; от аккаунта editor’а; Differ — gate). Runtime
пишет vault первым. Сайт `/queue` «Принять / Отклонить /
Доработать» по-прежнему решают **всю** заявку (ТЗ 3.08). Отклонить /
доработать / откатить — **на сайте** `/queue`. Свой предложение
принять нельзя.

**ТЗ 3.16 / 3.22.** У **одного** editor’а в работе **одна** карточка.
Пока качается или открыта текущая, остальные «Принять в работу»
выключены. Второй клик не запускает второй запрос. Слот снимают Save
& Resolve или **«Отменить»**. Два и больше editor’ов работают
**параллельно на разных** карточках. Одну карточку в работу берёт
один; если слот только локальный — другим он не виден (серверный слот
«занято у @login» — leftover). Несколько карточек в кэше не копить.

**ТЗ 3.17 / 3.25.** После **успешной записи** принятого файла в vault
сравнение **закрывают** и открывают **эту локальную** заметку как
обычную заметку Obsidian (не MergeView). Если запись vault не удалась —
принятие не закончено, сравнение не закрывают как успех. Это обязательный
UX (ТЗ **3.25**), не leftover против 3.22. Слот «в работе» снимают;
очередь справа снова можно брать. Повторный API на уже **полностью**
принятой заявке — успех, не `this proposal cannot be accepted now`.

**ТЗ 3.18.** Save & Resolve принимает **одну** карточку. Если в заявке
два и больше файлов — соседние строки очереди **остаются**. Один
accept не снимает вторую карточку. Сайт `/queue` «Принять» не меняется
(вся заявка, ТЗ 3.08). Две операции после принятия — ТЗ **3.25** (не
равнять принятие с POST в общую).

**ТЗ 3.19 / 3.25.** После принятия файла — **две операции**.

1. Смерженный Markdown **всегда** пишут в локальный vault как обычную
   заметку по пути карточки (тот же путь, что у файла заявки, например
   `Нарциссизм.md`; родительские папки создают). Это хранилище Obsidian
   editor’а — законная локальная копия принятой карточки, не кэш
   `.obsidian/plugins/…/work/` и не вторая каноническая общая. Если
   запись не удалась — принятие не закончено. Editor **открывает эту
   локальную заметку новым листом** обычного редактора Markdown:
   `createLeafBySplit` или `getLeaf(true)` + `openFile` **только если
   этот лист не MergeView**; `getLeaf('tab')` — только когда он тоже
   не сравнение; запасной путь — `openLinkText` по имени карточки, затем
   `workspace.openFile` если API есть. `revealLeaf` / `setActiveLeaf`
   после успешного `openFile`. Сравнение закрывают **только после** того,
   как эта заметка — активный вид.
2. Затем сравнивают этот локальный файл с файлом в хранилище ризомы.
   Если **отличаются** — вторая операция: обновить хранилище **от
   аккаунта editor’а** (доступ к общей; Differ — write gate). Если
   **одинаковые** — вторую операцию пропускают.

Очередь справа **перечитывают на месте**, не забирая фокус у новой
вкладки. Каждый шаг (запись vault, сравнение с складом, обновление
хранилища или пропуск, getLeaf, openFile, закрытие сравнения) пишут в
`.obsidian/plugins/graphnotes-card-merge/debug.log` строкой
`время | шаг | OK/FAIL | деталь`. Notice «Карточка открыта: путь»
после успеха (15 с). На каждой ошибке — Notice 20 с с причиной
(запись — путь; open — тип листа и API; обновление хранилища —
статус ответа). Команда «GraphNotes: показать debug.log» — последние
30 строк. Если открыть не удалось — Notice с точным путём и ошибкой,
не молча оставаться на слиянии.

**Долг runtime (3.25).** Плагин сейчас POST `/api/proposals/{id}/resolve`
сначала, потом может записать vault (при обрыве POST 75 с vault не
пишут). Это не канон: локальная запись обязательна и первая. Новый
HTTP-глагол не выдумывать.

`GET /api/differ` и `GET /api/differ/files/{path}` — **сайт** вкладки
Сверка, не боковая панель плагина. Не выгрузка всей ризомы.

Не выдумывать `/api/differ/queue`. Список editor’а в плагине —
`GET /api/proposals`. Пара карточки — `GET /api/proposals/{id}/files/{path}`
(`{path, before, body}`, без wikidiff2). Сайт `/queue` по-прежнему читает
`GET /api/proposals/{id}` с таблицей wikidiff2. Технический editor
проверяет: Bearer `personal:read` на список и пару; runtime POST
`/resolve` — Bearer роли `editor` / `admin` после записи vault, если локальный ≠ общая; approve/reject/request-changes/rollback —
cookie сайта; кэш сравнения — в `.obsidian/plugins/…/work/`, не принятая
заметка; принятая карточка — обычная заметка vault (ТЗ **3.25**, две
операции). Новый HTTP-глагол не выдумывать.

Сайт 3.11 / 3.13: вкладка **Сверка** `#/differ` — исходящий список и
«Из ризомы»; `/offer` — только заявки; «Текст сверки» снята.
`POST /api/differ/inbound/{path}/accept` копирует опубликованную общую
в личный склад. Card Merge leftover (модалка / `GET /api/differ`) —
у агентов плагина, не этот контур.

#### 6.6.5. Входящие правки по своим карточкам (ТЗ 3.13)

Конфликт, который закрывает этот пункт: автор отдал карточку в общую,
Differ исходящий по этому пути опустел, и он больше не видит, что
карточку в ризоме кто-то изменил. Ему нужно **следить** за такими
карточками и при желании забрать новую общую в своё хранилище.

**Кого уведомлять.** Автора, у которого этот путь уже входил в
**принятое** предложение (создание или правка). Подписка автоматическая,
отдельного «follow» нет. Карточки, которые он только читал и никогда не
отдавал, сюда не входят — это не ZIP общей и не `take-from-shared`.

**Где уведомление.** Вкладка **Сверка** (`#/differ`), второй список
**«Из ризомы»**. Плюс, если автор включил галочку или ползунок
**«Получать уведомления об изменениях в карточках, которые вы правили»**
(§5.5.6 / ТЗ **3.15**), — письмо и Telegram тем же контуром (SMTP / бот,
не вход). Ссылка в письме — `#/differ`. Один раз на появление входящей
строки. Плагин автора этот список не читает.

**Когда строка появляется.** Путь в его подписке, тело опубликованной
общей ≠ тело в его личном складе. Обычно после чужого принятого
предложения или правки editor’а по этому пути.

**Что можно сделать.** Добровольно **принять в своё хранилище**:
опубликованная общая копируется в его личный склад на этот путь.
Не построчный merge, не предложение в общую, не запись в vault из
плагина. Можно не принимать — принудительной записи нет.

**Не мешать с исходящим.** Пока путь во входящем списке, его **нет** в
«предложить в ризому». Иначе он случайно накатит свою старую личную
копию поверх уже принятых чужих правок. Когда примет (или сам допишет
личное так, что тексты совпадут) — входящее пустеет. Дальше он снова
правит у себя и предлагает исходящим Differ, как в 3.11.

**Leftover.** Обратная выгрузка **всего** склада → vault (ТЗ 2.93) не
этот канон. **ТЗ 3.30** — только **выданная** карточка: после
появления гранта плагин скачивает её в vault
(`GET /granted*`; runtime leftover если ещё копируют в личное). После inbound Differ 3.13 сайт уже обновил личный
склад, а Obsidian ещё со старым файлом — та же дыра 2.91 «локальное
побеждает», пока download не поставлен. Сайт-редактор по-прежнему выключен.
Three-way merge нет. Поправка ADR-009 — у владельца, не у агента. ТЗ
**3.24** называет будущий клиентский unlock (следить в БД + принять
входящее в плагине) под покарточной моделью, не ставит его в runtime.

#### 6.6.6. Покарточный API, грант и один плагин (ТЗ 3.24 / **3.26** / **3.30**)

**ТЗ 3.26 — один плагин уже канон**, не направление 3.23 и не «намеченный
клиент потом». ТЗ **3.09** снят. Каталог `obsidian-plugin/` leftover.
Поставленный один клиент — `obsidian-card-merge/`. Склейку двух каталогов
в коде в этой волне не делать, если ещё не сделана.

**ТЗ 3.30 сужает 3.24.** Вопрос «API покарточное?»: эндпоинты GET/PUT
этот путь; авторизация — грант в БД: `(user_id, card_path)` **или**
`(user_id, tag)` **или** `(user_id, path_prefix)` на запрос. Write, если
прямой путь или любой тег карточки совпал или путь под префиксом папки.
Не ACL в markdown. Не «права живут на карточке» как
primary. Срез editor’а и user с 1–10 карточками — один механизм.
**Смена 3.21:** пустой список тегов ≠ вся очередь; нет гранта = нет
дополнительной записи в общую. Empty не clone корпуса.
**ТЗ 3.30:** write-grant = право на **один серверный файл** общей.
Личное — только невыданные черновики. Vault — клиентская копия. Очередь
чужих — только с editor-capability. «Три копии, потом схлопнуть» снято.
Список/очередь/файл/sync — одна функция; нет гранта → 404/403. Общая
живёт отдельно от любой учётки. **OPEN:** read-без-write очереди;
грант по исходному автору.

**Что есть сейчас (runtime).** Один клиент `obsidian-card-merge/`:
автор (`user`) пишет невыданные черновики в личное тем же sync и
предлагает в общую (`can_propose_to_rhizome`); очередь editor’а —
`can_see_queue`. У `editor` / `admin` офер сегодня выкл. (ТЗ **3.27**,
user-only для невыданных). Формула «учётка и есть ризома» **снята**.
leftover-каталог `obsidian-plugin/` не канон. Общие карточки на сайте
только чтение (ТЗ 2.93). Editor/admin не принимают своё. ТЗ **3.25**:
общее целиком в vault не клонируют; после принятия — две операции
(локально, затем тот же серверный файл если отличается).
`GET/POST /api/admin/grants`, `DELETE /api/admin/grants/{id}`,
`GET /api/admin/grants/catalog`, `PATCH /api/admin/users/{id}/editor-tags`
и фильтр очереди/файла — эта волна. **Долг runtime:** `personal_uploads` + `shared_notes`
на один выданный путь.

**Клиент одного плагина (канон 3.26).** Невыданные черновики — sync как
у участника; выданные — download + sync в тот же shared файл; очередь
из API при editor-доступе на карточку. Не `take-from-shared` корпуса.
Vault не вторая ризома и не «диск = ризома».

**Нужен ADR:** один плагин снимает 3.09; грант API (3.30 сужает 3.24).
Открытые вопросы — [access.md](access.md) §5.6.7,
[roadmap-and-governance.md](roadmap-and-governance.md) §12 п. 12.

### 6.7. Публикация в общественную ризому

Адрес очереди editor’а — **`/queue`**. **Мои** предложения автора —
**`/offer`**. Не смешивать (ТЗ 2.58 снял вывод 2.57 про один экран).
Не выдумывать `/accepted/differ`.

```text
git пользователя
  -> Differ
      -> выбранные отличия
          -> предложение (Git-backed)
              -> очередь editor’ов
                  -> сначала текст карточек и связи, затем ризома (Graph Diff)
                      -> принять / отклонить / вернуть / откатить
                          -> merge в общую ризому
                              -> webhook/reconciliation
                                  -> переиндексация
                                      -> Differ пустеет по принятым путям
```

Несколько предложений по одному файлу остаются параллельными, пока editor не
сольёт одно из них. Last-write-wins в PostgreSQL запрещён.

Пользователь должен иметь возможность:

- увидеть Differ своего личного склада к опубликованной общей ризоме;
- выбрать отличия чекбоксами и создать предложение;
- увидеть пометки Differ на своих личных карточках, которых в общей нет
  («дай, если хочешь»), и предложенные темы для новой карточки (§6.6.3);
  сначала кабинет, затем тот же список в плагине (ТЗ 2.88);
- увидеть состояние предложения без GitHub-жаргона;
- увидеть свой авторский вклад после принятия, а не только пустой Differ.

Editor должен иметь возможность:

- увидеть очередь в трёх вкладках: **Новые**, **В работе**, **Отклонённые**;
- открыть **одну** заявку (остальные свёрнуты); внутри — **одна** карточка
  с текстом, остальные заголовком (ТЗ **3.08**);
- под каждой карточкой — **Принять / Отклонить / Доработать**; кнопки решают
  всю заявку, не один файл;
- открыть предложение с **текста карточек и связей**, затем ризому;
- отклонить или вернуть автору **с комментарием**; возвращённое — «В работе»,
  непринятое — «Отклонённые»;
- увидеть список и автора предложений;
- просмотреть человеческий текстовый diff **как у Википедии**, посчитанный
  **wikidiff2** (ТЗ 3.03): две колонки; новая карточка — слева пусто; не
  сырой unified и не только готовый Markdown предложения;
- увидеть, какие заметки и связи автор предлагает, и добавленные/удаленные
  узлы и связи (в объеме стадии / Stage 8);
- принять, отклонить, вернуть, откатить;
- увидеть статус конфликта, не скрывая необходимость разрешения;
- **получить уведомление о новых правках в очереди**, если сам включил канал
  (§5.5.6): письмо при рабочем SMTP и/или Telegram, когда задан токен бота.
  Событие — новое предложение попало в очередь. По умолчанию выключено
  (не спамить). Автор своего предложения не получает это уведомление.
- автор **получает уведомление об изменениях в карточках, которые
  правил** (ТЗ 3.15 / §6.6.5), если включил одну галочку/ползунок в
  Настройках: почта и Telegram; ссылка `#/differ`; не очередь editor’а.

После merge общественный индекс обязан соответствовать merged commit SHA.
Публикация должна быть атомарной на границе чтения: до завершения индексации
видна предыдущая полная общая revision, после завершения — новая полная
revision. Частично обновлённая общая ризома пользователям не показывается.

### 6.8. Аудит и восстановление

- значимые действия журналируются **в базе GraphNotes** (таблица событий
  учётки), а не только в stdout контейнера. Это канон журнала продукта.
- в записи: кто сделал (UUID), роль на момент действия если известна, кого
  затронули, какое действие, когда; при необходимости связь с proposal / Git
  revision / слоем;
- обязательно в журнале, среди прочего: регистрация; вход (успех/отказ);
  выход; смена роли; блокировка; **смена пароля admin’ом**; **сброс пароля
  по почте**; решения editor по предложениям; уведомления очереди (без
  адресов и секретов, только счётчики каналов); **создание и отзыв токена
  плагина**; **фиксация передачи в личное** (UUID, token id, transfer id,
  пути, версии, размеры, результат — без секрета токена и без тел заметок);
- отдельно от admin-журнала владелец на `/user` видит **свою** историю
  входов с токеном плагина за ~6 месяцев, не дольше года (кто / IP /
  какой токен). Это не чужой журнал и не тела заметок (ТЗ 2.73–2.74).
  Отдельная база логов — позже, не вторая ризома и не Redis;
- **никогда** в журнале: открытый пароль, `password_hash`, cookie, refresh
  token, SMTP-секреты, секрет токена интеграции, тела Markdown;
- журнал читает только `admin` (экран на вкладке «Администрирование»);
  `user`/`editor` чужой журнал не видят;
- GitHub сохраняет техническую историю commit/PR; это не замена журнала
  GraphNotes;
- авторский вклад (заметки, связи, предложения) доступен как продуктовая
  история, а не только как скрытый admin-аудит;
- журнал действий — не тела заметок и не второй канон Markdown;
- должна существовать ручная безопасная пересборка производного индекса;
- повторная обработка webhook не должна создавать дублирующее состояние;
- **стартовая карточка** `/card` (**вывод:** UUID или git-путь) живёт в
  настройках инсталляции GraphNotes, экран Admin → **Установка**; пишет
  только `admin`. Если не задана — `/card` без пути отвечает 404. Не папка
  слоя и не настройки учётки.
