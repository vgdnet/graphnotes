## 10. За пределами MVP без отдельного решения

- Telegram, Google/GitHub OAuth и другие внешние identity providers
  (своя почта на своём SMTP — §6.1.2, следующая версия, не этот пункт;
  **учётка vsepsy.ru на rhizome.vsepsy.ru** — §6.1.3, не Google/Telegram OAuth);
- Neo4j;
- Elasticsearch **до первой утверждённой выкатки на production `rhizome`**
  (итерация поиска — ADR-015; начинается **только после** этой выкатки,
  не этот стек Compose; до тех пор SQL);
- Redis, Celery, RabbitMQ и другие очереди/брокеры;
- S3/MinIO как обязательная инфраструктура;
- Dropbox / Google Drive и прочие внешние диски **в этой волне** (ТЗ 2.62:
  когда появятся — только коннекторы, копирующие `.md` в локальный склад,
  не второй канон и не замена GraphNotes);
- собственный Git-сервер или собственный merge-движок;
- Gitea/GitLab;
- Kubernetes;
- полноценный собственный UI ручного three-way merge;
- real-time collaborative text editing;
- хранение или merge канонического `graph.json`;
- редактор GraphNotes «как замена vault» (autocomplete `[[ ]]`, backlinks,
  локальный граф как продукт). Тонкий in-app редактор на сайте **выключен**
  (ТЗ 2.93 / §6.5.2), пока нет обратной выгрузки склада → пользователь.
  Когда появится обратная загрузка / синхронизация — включают редактуру
  **своей** личной. Когда можно будет взять карточку другого участника себе
  в ризому — для тех карточек редактура и обратная синхронизация. Не общая
  карточка, не второй Obsidian, не исторический `take-from-shared` без
  нового решения. GraphNotes для авторов — публикатор Markdown с правами и
  одной общей ризомой (ТЗ 2.61 / аналог Obsidian Publish), не клон редактора;
- канонические тела **опубликованной общей** в PostgreSQL и кнопки
  «скопировать заметки в общую» в обход Differ и очереди editor’ов.
  Личный Markdown на складе GraphNotes (загрузки / плагин) — **основной**
  путь, не запрет (ТЗ 2.61); in-app правка на сайте — leftover до
  обратной синхронизации (ТЗ 2.93);
- запись GraphNotes в personal git выбранных общих заметок и выгрузка
  опубликованной общей ZIP/clone как UX (исторический take-from-shared и
  «Скачать» ZIP; продуктовый путь снят). Общая читается в приложении;
- склейка двух leftover-каталогов `obsidian-plugin/` + `obsidian-card-merge/`
  в один пакет **в коде** (канон одного плагина — ТЗ **3.26**; runtime
  ещё два каталога). Покарточный ACL-blob в markdown в runtime (ТЗ **3.24**
  сужен **3.30** / §6.6.6 / §5.6.7) — **не эта волна**. Модель: API
  по карточке, авторизация грантом, один серверный файл. Очередь —
  capability того же клиента при editor-доступе на карточку. Входящее
  на сайте (3.13) для людей без write-grant; принятые карточки editor
  держит клиентской копией в vault (3.25: две операции после принятия;
  3.22 сужен: не dump корпуса и не вторая каноническая общая). Не
  возвращать `take-from-shared`;
- антипарсинг гостевого чтения общей (§16 / ТЗ 2.80) **до** первой
  выкатки на `rhizome`; на `rhizome-test` не включать;
- инвайты на регистрацию (§17 / ТЗ 2.85–2.87) **поставлены на
  `rhizome-test`** (2.89). На production `rhizome` — только после
  отдельного решения.

## 11. Актуальная стадийность

Точные границы, ветки и Definition of Done стадий определяются
`docs/context/MASTER_CONTEXT.md`, `docs/context/STAGE_STATUS.md` и активным
`docs/stages/STAGE<N>.md`.

Каноническая последовательность:

1. Stage 0 - Infrastructure;
2. Stage 1 - Project Bootstrap;
3. Stage 2 - Password Authentication;
4. Stage 3 - GitHub Integration (shared repo + connect personal git);
5. Stage 4 - Take from shared / ZIP fallback (исторически DONE; продуктовый
   путь take-from-shared / take-into-git снят ADR-009);
6. Stage 5 - Graph Engine;
7. Stage 6 - Shared graph + personal overlay;
8. Stage 7 - Differ, editor proposal queue / merge / rollback;
9. Stage 8 - Graph Diff (structural view of Differ/proposal);
10. Stage 9 - Production Hardening / CI/CD;
11. следующая продуктовая волна после первой версии — авторский вклад,
    provenance, Differ, карточки, статистика; **поиск Elasticsearch**
    (ADR-015) — **только после первой утверждённой выкатки на production
    `rhizome`**; вопросы §6.5.3 остаются на ту волну. До тех пор
    SQL-поиск. SMTP входа (§6.1.2 / ADR-017) поставлен в 2.37. Точный
    Stage-файл назначает владелец; это не Stage 9 hardening.

План веток из PDF версии 1.2 считается историческим и не заменяет этот roadmap.

## 12. Открытые продуктовые вопросы

Следующие идеи обсуждаются, но не считаются принятыми требованиями до явного
решения:

1. Минимальный provenance на узле/ребре (автор, слой, revision).
   (Принято 2026-08-29, ТЗ 2.0: автор — единица вклада; §3.5, §6.6.2.
   Нужен ADR; до ADR реализация не стартует как новая архитектура.)
2. Цвета состояний shared / personal / added / removed / unresolved / proposed.
3. Differ — одностороннее сравнение personal → published shared; предложение
   создаётся из выбранных отличий, не из всего vault. Обратного пути «забрать
   общую файлами» нет (ни ZIP «Скачать», ни clone как UX). take-from-shared /
   take-into-git не являются продуктовым путём. Правила слияния — §6.6.1.
   (ADR-009 частично: Differ; ZIP общей снят ТЗ 2.5, нужен ADR.)
4. Personal remote — отдельный GitHub repository (не fork общей). Первый
   тестовый binding: GraphNotes user `efimov` → `vgdnet/guide_psy`; общая
   ризома → `vgdnet/rhizome`.
5. Редактирование непосредственно через граф — вне MVP, пока нет ADR.
6. Совместное редактирование текста в реальном времени — вне MVP.
7. Какие поля карточки автора (и карточки психолога на vsepsy.ru) можно
   выставить **всему интернету** в ачивке / «данных для моего сайта».
   Каркас §6.1.4 принят (граф или счётчики, opt-in, не ZIP). Состав полей —
   отдельное решение владельца.
8. Поиск следующей итерации (ADR-015): **когда** закрыто — только после
   первой утверждённой выкатки на production `rhizome`. Тела в индексе,
   сниппеты гостю, личный слой, морфология, фасеты, где крутится
   Elasticsearch — открытые вопросы 1–9 в §6.5.3; ответы не выдумывать.
   Пока нет ответов и нет той волны, в код ES не идём. До тех пор SQL.
9. Открытый чужой личный репозиторий как вторая публичная поверхность:
   все ищут, находят и комментируют личные заметки без очереди editor’ов.
   Продуктолог (2026-09-04) это **не принял**: ломает «ровно одна общая»
   и §3.3. Принято только: закрытый срез в том же git + вид «ризома автора»
   после уровня (§5.6.4). Чтобы открытый личный стал витриной — явное
   решение владельца и ADR к ADR-007 / §3.3.
10. Режим сравнения **построчно в Differ** (автор выбирает, что предложить):
    unified / split владелец ещё не зафиксировал. Не проектировать в коде.
    **Принятие правок редактором** закрыто ТЗ **3.02 / 3.03**: таблица как у
    Википедии, движок **wikidiff2** (ADR-018). Переключателя inline нет.
    Режим **по смыслу** (нейросеть)
    — отдельный ADR, не текущая стопка карточек (ТЗ 2.56).
11. Лендинг **`/`**: владелец не переопределил. Канон §5.6: `/` → `/graph`
    (ТЗ 2.58).
12. Покарточный API и грант (ТЗ **3.30** сужает **3.24** / §5.6.7 /
    §6.6.6): **эндпоинты** GET/PUT этот путь; **авторизация** —
    `(user_id, card_path)` или `(user_id, tag)` или `(user_id, path_prefix)`
    в БД общей на запрос.
    Не ACL в markdown. Не «права живут на карточке». Срез editor’а =
    user с N карточками. **Смена 3.21 (явно):** пустой список ≠ вся
    очередь; нет гранта = нет дополнительной записи в общую. **ТЗ 3.30:**
    один серверный файл выданной карточки **сейчас** (грант = право на
    общий объект; личное = невыданные черновики; vault = клиент).
    Очередь — только с editor-capability. «Три копии, потом схлопнуть»
    снято. Общая отдельно от любой учётки. Диск vault = ризома — не
    канон. Runtime: две таблицы на один путь leftover. **ТЗ 3.26:** один
    плагин. **OPEN:** read-без-write очереди; editor-срез vs editor-автор
    карточки B; платный мейкер; ADR-016; ADR-007; грант по исходному автору.
    **Нужен ADR:** один плагин снимает 3.09; грант API. Не
    `take-from-shared`.

Ответ, который меняет продуктовую модель, security boundary, источник истины
или внешний контракт, оформляется ADR.

## 13. Управление глобальными изменениями

### 13.1. Что требует ADR

ADR обязателен, если решение меняет хотя бы одно из следующего:

- источник истины или модель хранения;
- личный/общественный ownership и merge workflow;
- роли, security boundary или модель доступа;
- ключевую внешнюю систему;
- канонический технологический компонент;
- лицензию;
- topology окружений и promotion gate;
- совместимость публичного API или данных;
- границы MVP настолько, что меняется roadmap или Definition of Done нескольких
  стадий.

### 13.2. Что не требует ADR

Обычно ADR не нужен для локального исправления, внутреннего рефакторинга,
конкретной схемы endpoint внутри одной стадии, UI-детали без изменения
продуктовой семантики или замены библиотеки на совместимую реализацию.

### 13.3. Процесс принятия

```text
вопрос / спор
  -> варианты и последствия
      -> явное решение владельца проекта
          -> ADR со статусом Accepted (если глобально)
              -> продуктовое ТЗ (что видит человек)
                  -> техническое ТЗ (как устроено / как выкладывать)
                      -> Code Writer выкладывает на rhizome-test
```

Непринятое предложение не должно молча попадать в код как новая архитектура.
На тест не выкладывают раньше продуктового и технического ТЗ (ТЗ 2.99).

### 13.4. Поставленное поведение сразу в оба ТЗ

Любое **поставленное** изменение продукта, UX или поведения (новый экран,
переключатель, правило доступа, то, что видит человек на графе или в
настройках) в той же поставке записывается в **продуктовое ТЗ** (этот набор
файлов) и в **техническое ТЗ** (`MASTER_CONTEXT.md`, при необходимости
контекст Technical Observer и `docs/deployment/**`).

**ТЗ 2.99 — порядок, не «сначала тест»:**

1. **Продуктовое ТЗ** — принятое из обсуждения: экран, hash, кто видит,
   что делает.
2. **Техническое ТЗ** — контракт и выкладка (`MASTER_CONTEXT`,
   `docs/deployment/**` при необходимости).
3. **Code Writer** выкладывает на `rhizome-test` (`http://172.16.13.14:8080`).

Не выкатывать на тест, пока нет обоих ТЗ. Не дописывать ТЗ «после того
как уже на тесте». Чат, prompt и описание коммита спецификацией не являются.

**ТЗ 3.05 — канон всегда один.** Все агенты читают те же файлы. Нет
второго Markdown-канона и нет личного ТЗ у агента. Leftover в runtime
(в т.ч. `php-cli` вместо native wikidiff2) — дырка в коде, не канон.

Пока код и ТЗ расходятся, изменение не считается зафиксированным. Builder
не подменяет редакторов ТЗ: если правит код, передаёт формулировку
product-spec-editor и technical-spec-editor, чтобы они записали требование
и архитектурный контракт.

Тема оформления (светлая/тёмная, §5.5.4) — пример: UX без ADR, но оба ТЗ
всё равно называют поведение, хранение выбора, токены подписей графа и то,
что управление — **Theme Switcher** (таблетка солнце/луна), не текстовые кнопки.
