- Gitea/GitLab;
- Kubernetes;
- полноценный собственный UI ручного three-way merge;
- real-time collaborative text editing;

## 11. Актуальная стадийность

Точные границы, ветки и Definition of Done стадий определяются
`docs/context/MASTER_CONTEXT.md`, `docs/context/STAGE_STATUS.md` и активным
`docs/stages/STAGE<N>.md`.

Каноническая последовательность:

1. Stage 0 - Infrastructure;
2. Stage 1 - Project Bootstrap;
3. Stage 2 - Password Authentication;
4. Stage 3 - GitHub Integration (shared repo + connect personal git);
5. Stage 4 - Take from shared / ZIP fallback (исторически DONE; продуктовый
   путь take-from-shared / take-into-git снят ADR-009);
6. Stage 5 - Graph Engine;
7. Stage 6 - Shared graph + personal overlay;
8. Stage 7 - Differ, editor proposal queue / merge / rollback;
9. Stage 8 - Graph Diff (structural view of Differ/proposal);
10. Stage 9 - Production Hardening / CI/CD;
11. следующая продуктовая волна после первой версии — авторский вклад,
    provenance, Differ, карточки, статистика; **поиск Elasticsearch** (ADR-015),
    когда закрыты открытые вопросы §6.5.3. SMTP входа (§6.1.2 / ADR-017)
    поставлен в 2.37. Точный Stage-файл назначает владелец; это не
    Stage 9 hardening.

План веток из PDF версии 1.2 считается историческим и не заменяет этот roadmap.

## 12. Открытые продуктовые вопросы

Следующие идеи обсуждаются, но не считаются принятыми требованиями до явного
решения:

1. Минимальный provenance на узле/ребре (автор, слой, revision).
   (Принято 2026-08-29, ТЗ 2.0: автор — единица вклада; §3.5, §6.6.2.
   Нужен ADR; до ADR реализация не стартует как новая архитектура.)
2. Цвета состояний shared / personal / added / removed / unresolved / proposed.
3. Differ — одностороннее сравнение personal → published shared; предложение
   создаётся из выбранных отличий, не из всего vault. Обратного пути «забрать
   общую файлами» нет (ни ZIP «Скачать», ни clone как UX). take-from-shared /
   take-into-git не являются продуктовым путём. Правила слияния — §6.6.1.
   (ADR-009 частично: Differ; ZIP общей снят ТЗ 2.5, нужен ADR.)
4. Personal remote — отдельный GitHub repository (не fork общей). Первый
   тестовый binding: GraphNotes user `efimov` → `vgdnet/guide_psy`; общая
   ризома → `vgdnet/rhizome`.
5. Редактирование непосредственно через граф — вне MVP, пока нет ADR.
6. Совместное редактирование текста в реальном времени — вне MVP.
7. Какие поля карточки автора (и карточки психолога на vsepsy.ru) можно
   выставить **всему интернету** в ачивке / «данных для моего сайта».
   Каркас §6.1.4 принят (граф или счётчики, opt-in, не ZIP). Состав полей —
   отдельное решение владельца.
8. Поиск следующей итерации (ADR-015): тела в индексе, сниппеты гостю,
   личный слой, морфология, фасеты, где крутится Elasticsearch — список
   в §6.5.3. Пока нет ответов, в код ES не идём.
9. Открытый чужой личный репозиторий как вторая публичная поверхность:
   все ищут, находят и комментируют личные заметки без очереди editor’ов.
   Продуктолог (2026-09-04) это **не принял**: ломает «ровно одна общая»
   и §3.3. Принято только: закрытый срез в том же git + вид «ризома автора»
   после уровня (§5.6.4). Чтобы открытый личный стал витриной — явное
   решение владельца и ADR к ADR-007 / §3.3.
10. Режим сравнения в Differ **построчно**: как именно показывать строки
    (unified / split, какие правила предложения) владелец ещё не зафиксировал.
    Не проектировать в коде. Режим **по смыслу** (нейросеть) — отдельный ADR,
    не текущая стопка карточек (ТЗ 2.56).
11. Лендинг **`/`**: владелец не переопределил. Канон §5.6: `/` → `/graph`
    (ТЗ 2.58).

Ответ, который меняет продуктовую модель, security boundary, источник истины
или внешний контракт, оформляется ADR.

## 13. Управление глобальными изменениями

### 13.1. Что требует ADR

ADR обязателен, если решение меняет хотя бы одно из следующего:

- источник истины или модель хранения;
- личный/общественный ownership и merge workflow;
- роли, security boundary или модель доступа;
- ключевую внешнюю систему;
- канонический технологический компонент;
- лицензию;
- topology окружений и promotion gate;
- совместимость публичного API или данных;
- границы MVP настолько, что меняется roadmap или Definition of Done нескольких
  стадий.

### 13.2. Что не требует ADR

Обычно ADR не нужен для локального исправления, внутреннего рефакторинга,
конкретной схемы endpoint внутри одной стадии, UI-детали без изменения
продуктовой семантики или замены библиотеки на совместимую реализацию.

### 13.3. Процесс принятия

```text
вопрос / спор
  -> варианты и последствия
      -> явное решение владельца проекта
          -> ADR со статусом Accepted
              -> обновление PRODUCT_SPEC / MASTER_CONTEXT
                  -> обновление затронутых Stage-документов
```

Непринятое предложение не должно молча попадать в код как новая архитектура.

### 13.4. Поставленное поведение сразу в оба ТЗ

Любое **поставленное** изменение продукта, UX или поведения (новый экран,
переключатель, правило доступа, то, что видит человек на графе или в
настройках) в той же поставке записывается в **продуктовое ТЗ** (этот набор
файлов) и в **техническое ТЗ** (`MASTER_CONTEXT.md`, при необходимости
контекст Technical Observer и `docs/deployment/**`).

Обсуждение в чате, prompt или описание коммита спецификацией не являются.
Пока код и ТЗ расходятся, изменение не считается зафиксированным. Builder
не подменяет редакторов ТЗ: если правит код, передаёт формулировку
product-spec-editor и technical-spec-editor, чтобы они записали требование
и архитектурный контракт.

Тема оформления (светлая/тёмная, §5.5.4) — пример: UX без ADR, но оба ТЗ
всё равно называют поведение, хранение выбора, токены подписей графа и то,
что управление — **Theme Switcher** (таблетка солнце/луна), не текстовые кнопки.
