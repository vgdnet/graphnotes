## 1. Назначение документа

Этот документ фиксирует согласованное продуктовое техническое задание
GraphNotes: назначение продукта, пользовательские роли, функциональные
требования, границы MVP и критерии приемки.

Документ создан на основе PDF `GraphNotes_TZ_GitHub_Password_MVP_RU.pdf`, версия
1.2 от 2026-08-15. Более новые принятые решения из ADR и канонического контекста
репозитория имеют приоритет над положениями исходного PDF.

Документы имеют разные зоны ответственности:

- `docs/product/PRODUCT_SPEC.md` - что и для кого должен делать продукт;
- `docs/context/MASTER_CONTEXT.md` - текущая каноническая архитектура;
- `docs/decisions/ADR-*.md` - почему принято глобальное решение и каковы его
  последствия;
- `docs/context/STAGE_STATUS.md` - фактическое состояние реализации;
- `docs/stages/STAGE<N>.md` - исполнимое задание конкретной стадии.

ТЗ не является журналом переписки. Обсуждаемое глобальное изменение становится
каноническим только после явного решения: создается или обновляется ADR, затем
синхронно обновляются затронутые разделы ТЗ и `MASTER_CONTEXT.md`.

## 2. Видение продукта

GraphNotes — слой общей ризомы над Markdown в Git, а не второй Obsidian.
Люди пишут заметки в своём vault (часто Obsidian + obsidian-git или аналог).
GraphNotes показывает одну общую ризому графом, даёт скачать её актуальным
ZIP и даёт группе editor’ов собрать одну общую ризому из того, что Differ
нашёл в git пользователя и чего ещё нет (или что отличается) в общей.

Круговорот Markdown:

```text
написал статью в своём git
  -> Differ нашёл отличия к общей ризоме
      -> предложил выбранное
          -> очередь editor’ов
              -> приняли в общую
                  -> Differ снова сравнил
                      -> отличий нет
```

Обратно пользователь забирает общую ризому файлами: ссылка «Скачать» отдаёт
ZIP опубликованной общей revision. Кладка этого ZIP в личный git — вне
текущего MVP. Публичный clone knowledge repository по-прежнему не требует
аккаунта GraphNotes.

Ценность продукта — живой граф, Differ и человеческая очередь слияния, а не
клон редактора заметок и не обёртка над GitHub PR.

См. ADR-008 и ADR-009.

## 3. Неподвижные продуктовые принципы

### 3.1. Markdown - источник истины

Каноническое знание хранится в Markdown. Узлы, связи, теги, поисковый индекс и
визуальный граф являются производными данными.

```text
Markdown в Git
  -> parser
      -> PostgreSQL index
          -> Graph API
              -> Web UI
```

Запрещено вводить параллельный канонический `graph.json`. Слиянию и
версионированию подлежит Markdown; после изменения Git-состояния граф
переиндексируется.

### 3.2. Личный и общественный слои

- в одной инсталляции существует ровно одна общая ризома;
- у каждого пользователя существует ровно одна личная ризома — это **его
  собственный Git-репозиторий**, а не vault внутри PostgreSQL и не обязательная
  ветка `user/<uuid>` на общем репозитории;
- личный слой содержит Markdown пользователя в его git;
- общий слой содержит утверждённое коллективное знание в одном knowledge
  repository (ADR-007);
- личный граф — проекция личного Markdown в git пользователя плюс связи с
  общей ризомой; не отдельный файл;
- общественный граф — проекция утвержденного Markdown общей ризомы;
- сравнение слоёв — это сущность **Differ**: односторонние отличия личного
  git относительно опубликованной общей ризомы (ADR-009).

Личная и общая ризомы — два Git-источника и уровни ответственности, а не две
таблицы заметок. Workspace, organization, team, community и несколько общих
ризом не входят в текущую модель.

Каноническая формула: **«Личная ризома — git человека; единая общая ризома —
проверенное коллективное знание в одном репозитории».**

### 3.3. GitHub скрыт за продуктовым UX

GitHub используется как внешний Git-движок для репозиториев, веток, коммитов,
истории, diff, Pull Request и merge. Обычный пользователь работает с понятиями
«скачать», «личная ризома», «общая ризома», «отличия», «предложить в общую» и
«принять / отклонить / откатить», а не с branch, SHA и Pull Request.

### 3.4. Граф не является границей безопасности

Разделение веток или визуальных слоев само по себе не обеспечивает изоляцию.
Права проверяются backend на основании внутреннего UUID пользователя и
глобальной роли. Credentials GitHub App пользователям не выдаются.

Публичный clone/fetch общей knowledge repository, если репозиторий открыт на
чтение, не требует аккаунта GraphNotes (ADR-008). Действия записи через
приложение (подключить git, предложить из Differ, editor) требуют аккаунта.
Скачать ZIP опубликованной общей ризомы — чтение, как граф: без логина, если
knowledge repo публичный.

## 4. Термины

| Термин | Определение |
| --- | --- |
| Заметка | Markdown-файл и его индексированное представление |
| Узел | Производное представление заметки или unresolved-ссылки в графе |
| Связь | Производное направленное отношение между заметками из Markdown-ссылки |
| Личная база | Git пользователя (обычно Obsidian vault + obsidian-git) и его производный граф |
| Общая ризома | Единственное утвержденное коллективное Markdown-состояние в одном knowledge repository и его производный граф |
| Скачать | ZIP Markdown опубликованной общей revision (то же состояние, что видит граф) |
| Differ | Производное одностороннее сравнение личного git с опубликованной общей ризомой: что пользователь может отдать в общую |
| Предложение | Git-backed заявка из выбранных результатов Differ в общую ризому, очередь editor’ов |
| Graph diff | Структурный вид Differ/предложения: добавленные, удаленные или измененные узлы и связи |
| Unresolved link | Ссылка на заметку, которой еще нет в выбранном состоянии |

## 5. Глобальные пользовательские роли

GraphNotes MVP использует три глобальные иерархические роли:
`user < editor < admin`.

### 5.1. User

- регистрируется и входит по логину/паролю, чтобы вносить вклад через GraphNotes;
- читает единую общую ризому (в приложении и, если репозиторий публичный, клоном
  git без аккаунта);
- подключает свой git как личную ризому;
- скачивает ZIP опубликованной общей ризомы;
- видит Differ: односторонние отличия своего git к общей ризоме;
- создаёт предложение из выбранных отличий Differ;
- видит граф общей ризомы и overlay связей своего git с ней.

Авторство заметок в MVP происходит во внешнем редакторе (Obsidian или аналог),
не во встроенном клоне Obsidian.

### 5.2. Editor

- имеет все права `user`;
- рассматривает очередь предложений: принять, отклонить, вернуть, откатить;
- видит автора, человеческий текстовый diff, состав Differ и (Stage 8) Graph Diff;
- может зафиксировать правку общей ризомы аудируемым Git commit без требования
  полноценного in-app редактора;
- не может принять собственное предложение;

### 5.3. Admin

- является суперпользователем и имеет все права `user` и `editor`;
- управляет пользователями, ролями, блокировками и системными настройками;
- управляет привязкой GitHub-ресурсов и пересборкой индекса;
- видит системный аудит;
- рассматривает предложения и может зафиксировать аудируемый Git commit в общую
  ризому без требования in-app редактора;
- административные и редакторские действия обязательно аудируются;
- не может обходить Markdown/Git source of truth и правила согласованности.

Только `admin` назначает и отзывает роли. Последний действующий
admin защищён от случайного удаления/блокировки или имеет проверенную recovery
процедуру. Ни один набор прав не может обходить Markdown/Git source of truth.

## 6. Функциональные требования MVP

### 6.1. Аутентификация

- GraphNotes использует собственную регистрацию и login/password;
- внутренний идентификатор пользователя - UUID;
- открытый пароль не хранится и не логируется;
- хранится только стойкий `password_hash`;
- поддерживаются login, logout, текущий пользователь и безопасный механизм
  продолжения сессии;
- пользователь может быть заблокирован без удаления данных;
- регистрация всегда создаёт `user` и не позволяет самостоятельно получить
  `editor` или `admin`;
- Telegram остается будущим optional identity provider, привязанным к
  существующему UUID, и не входит в MVP.

Минимальная модель пользователя:

| Поле | Назначение |
| --- | --- |
| `id` | Внутренний UUID |
| `username` | Уникальный логин |
| `password_hash` | Стойкий хеш пароля |
| `email` | Nullable-резерв для восстановления/уведомлений |
| `display_name` | Имя в интерфейсе |
| `role` | Иерархическая глобальная роль `user`, `editor` или `admin` |
| `is_active` | Состояние блокировки |
| `created_at`, `updated_at` | Служебные даты |

### 6.2. Единая общая ризома и два Git

- GraphNotes installation связывается с одним GitHub knowledge repository;
- утвержденное общее состояние соответствует его основной ветке;
- knowledge repository **может быть публичным на чтение**; clone/fetch тогда не
  требует аккаунта GraphNotes;
- личная ризома — подключённый git пользователя, не корпус заметок в PostgreSQL;
- backend выполняет GitHub-операции от имени приложения; App credentials
  пользователю не выдаются;
- commit SHA сохраняется в индексе для проверки согласованности;
- недоступность или rate limit GitHub отражается явным статусом синхронизации;
- публичность source repository GraphNotes не определяет visibility knowledge
  repository; visibility задаётся владельцем knowledge repo и проверяется до
  Stage 3 integration.

### 6.3. Скачать общую ризому и fallback-импорт

Первичный путь знания **из** общей ризомы к человеку — файлы: ссылка «Скачать»
отдаёт ZIP Markdown **опубликованной** общей revision (ADR-009). Это то же
состояние, которое показывает граф, а не сырой незаиндексированный HEAD, если
индекс отстал. Публичный git clone knowledge repository остаётся валидным и
не требует GraphNotes.

GraphNotes в MVP **не** записывает выбранные общие заметки в personal git
(исторический `take-from-shared` Stage 4 снят с продуктового пути). Кладка
скачанного ZIP в vault/git пользователя — вне текущего MVP.

ZIP/один `.md` **upload** — запасной ingest **в** подключённый personal git,
не замена git, не download и не in-app vault.

- скачать ZIP опубликованной общей ризомы;
- fallback: импорт одного `.md` или ZIP с проверкой путей, размера и бомб;
- канонические тела заметок не хранятся в PostgreSQL.

### 6.4. Индекс знаний

PostgreSQL хранит производный индекс и состояние приложения, включая как
минимум:

| Сущность | Минимальное назначение |
| --- | --- |
| `note_index` | Заметка, слой, владелец personal-слоя, Git-путь, title, slug, content hash, commit SHA |
| `note_links` | Источник, цель или unresolved title, тип и исходное представление ссылки |
| `tags`, `note_tags` | Нормализованные теги и отношения |
| `sync_jobs` | Репозиторий/ветка/revision, статус, ошибка и время синхронизации |
| `proposals` | Автор, base/head revisions, статус, решение, причина и audit linkage |

PostgreSQL не становится вторым источником Markdown и не хранит канонические
тела заметок. Индекс должен быть восстановим из канонического Git-состояния.

Производные данные обязаны различать:

- `shared` — опубликованную полностью индексированную общую revision;
- `personal` — revision ровно одного владельца;
- `proposal` — неопубликованный preview конкретных base/head revisions.

Proposed nodes, links, tags и properties не становятся shared до принятия и
завершения индексации merged revision.

### 6.5. Graph API и визуализация

Первая волна — граф **общей** ризомы. Личный граф нужен как overlay: как git
пользователя связан с общей ризомой.

Stage 5 поставляет производный индекс и ограниченный Graph API. Stage 6
добавляет Cytoscape и overlay. MVP должен предоставлять:

- общественный граф (без обязательного логина, если knowledge repo публичный);
- overlay связей подключённого личного git с общей ризомой;
- Differ как список односторонних отличий (Stage 7) и Graph Diff (Stage 8);
- узлы заметок и направленные связи;
- открытие исходного Markdown (чтение), не полноценный редактор;
- базовые фильтры;
- различимое отображение unresolved links;
- обработку пустого, изолированного и частично разрешенного графа;
- получение ограниченного подграфа без обязательной передачи всей базы при
  больших объемах.

Визуализация реализуется на React + TypeScript с Cytoscape.js, если новый ADR не
изменит это решение.

Не требуется в MVP: preview как в Obsidian, autocomplete `[[ ]]`, панель
backlinks, локальный граф текущей заметки как замена vault.

### 6.6. Differ

Differ — отдельная продуктовая сущность (ADR-009), а не экран GitHub и не
каноническое хранилище.

Входы: revision подключённого личного git и **опубликованная** общая revision.
Направление только **личный git → общая ризома**: «что этот пользователь может
отдать в общую?»

Отличие — Markdown-путь, которого нет в общей, либо путь есть в обеих и
содержимое разное. То, что есть только в общей, Differ не показывает: это
забирают скачиванием ZIP.

Пустой Differ значит: у этого личного git нет неопубликованного к общей.
После принятия editor’ом и успешной индексации общей эти пути из Differ
исчезают.

Пользователь отмечает чекбоксами **подмножество** результатов Differ и
создаёт предложение. Нельзя требовать «весь vault» и нельзя делать основным
управлением обязательное текстовое summary вместо списка отличий.

Differ считается из Git Markdown. Его нельзя материализовать как `graph.json`
или как тела заметок в PostgreSQL. Graph Diff (Stage 8) — структурный вид
того же набора (узлы, связи, unresolved), не вторая модель сравнения.

### 6.7. Публикация в общественную ризому

```text
git пользователя
  -> Differ
      -> выбранные отличия
          -> предложение (Git-backed)
              -> очередь editor’ов
                  -> текстовый diff / Graph Diff
                      -> принять / отклонить / вернуть / откатить
                          -> merge в общую ризому
                              -> webhook/reconciliation
                                  -> переиндексация
                                      -> Differ пустеет по принятым путям
```

Несколько предложений по одному файлу остаются параллельными, пока editor не
сольёт одно из них. Last-write-wins в PostgreSQL запрещён.

Пользователь должен иметь возможность:

- увидеть Differ своего git к опубликованной общей ризоме;
- выбрать отличия чекбоксами и создать предложение;
- увидеть состояние предложения без GitHub-жаргона.

Editor должен иметь возможность:

- увидеть список и автора предложений;
- просмотреть человеческий текстовый diff;
- увидеть добавленные/удаленные узлы и связи (в объеме стадии / Stage 8);
- принять, отклонить, вернуть, откатить;
- увидеть статус конфликта, не скрывая необходимость разрешения.

После merge общественный индекс обязан соответствовать merged commit SHA.
Публикация должна быть атомарной на границе чтения: до завершения индексации
видна предыдущая полная общая revision, после завершения — новая полная
revision. Частично обновлённая общая ризома пользователям не показывается.

### 6.8. Аудит и восстановление

- значимые действия пользователя и редактора журналируются;
- GitHub сохраняет техническую историю commit/PR;
- GraphNotes хранит бизнес-события и связь с Git revision;
- должна существовать ручная безопасная пересборка производного индекса;
- повторная обработка webhook не должна создавать дублирующее состояние.

## 7. Черновой контракт API MVP

Точные схемы, коды ошибок и авторизация определяются стадиями. Следующие маршруты
фиксируют продуктовую поверхность, но не требуют преждевременной реализации.

```text
POST /api/auth/register
POST /api/auth/login
POST /api/auth/refresh
POST /api/auth/logout
GET  /api/users/me

GET  /api/repository/status

POST /api/personal/connect
POST /api/personal/import-md          # fallback upload into personal git
GET  /api/personal/notes              # read-only index of connected git
GET  /api/personal/notes/{id}

GET  /api/shared/archive              # ZIP of published shared Markdown
GET  /api/differ                      # one-way personal → published shared

GET  /api/graph/shared                # Stage 5; login not required
GET  /api/graph/personal              # Stage 5; caller's layer only
GET  /api/graph/personal-overlay      # Stage 6
POST /api/index/rebuild               # admin, Stage 5
GET  /api/graph/diff?proposal_id=...  # Stage 8 structural view of Differ/proposal

POST /api/proposals
GET  /api/proposals
GET  /api/proposals/{id}
POST /api/proposals/{id}/approve
POST /api/proposals/{id}/reject
POST /api/proposals/{id}/request-changes
POST /api/proposals/{id}/rollback

POST /api/webhooks/github
```

Изменение API-контракта в ходе проектирования стадии допустимо без отдельного
ADR, если не меняет продуктовую модель или внешние интеграционные обязательства.

## 8. Критерии приемки MVP

MVP считается функционально готовым, когда:

- пользователь регистрируется и входит по логину/паролю для вклада через UI;
- открытый пароль нигде не хранится;
- публичный clone общей knowledge repository не требует аккаунта GraphNotes;
- пользователь подключает свой git и видит Differ к опубликованной общей ризоме;
- пользователь скачивает ZIP опубликованной общей ризомы;
- ZIP/MD upload остаётся безопасным fallback в personal git, не основным vault;
- система индексирует wikilinks, Markdown-ссылки, теги и unresolved links;
- индекс связан с конкретной Git revision;
- пользователь видит граф общей ризомы и overlay связей своего git;
- пользователь создает предложение из выбранных результатов Differ;
- editor видит человеческий текстовый diff и graph diff/preview;
- editor принимает, отклоняет, возвращает или откатывает с причиной;
- editor/admin не может принять собственное предложение;
- после merge общественная ризома переиндексируется до merged revision;
- читатели никогда не видят частично применённое предложение;
- PostgreSQL-индекс может быть восстановлен из Markdown/Git;
- канонические тела заметок не живут в PostgreSQL;
- ни один graph-файл не используется как параллельный источник истины;
- применимые security, migration, backup и deployment проверки текущих стадий
  выполнены на `rhizome-test` до продвижения на `rhizome`.

## 9. Нефункциональные требования

### 9.1. Безопасность

- все операции проверяют аутентификацию, глобальные назначения, ownership личной
  ризомы и тип слоя;
- секреты не коммитятся и не возвращаются в API/логи;
- загрузки ограничены и защищены от traversal и архивных бомб;
- webhook GitHub проверяется криптографически;
- GitHub credentials имеют минимально необходимые права;
- deployment Git-доступ на `rhizome` только read-only без push-capable
  credentials;
- backend и PostgreSQL не публикуются в LAN/DMZ без отдельного решения.

### 9.2. Надежность и согласованность

- операции синхронизации имеют наблюдаемый статус и понятную ошибку;
- webhook и фоновые reconciliation-операции идемпотентны;
- при расхождении Git и индекса побеждает каноническое Git/Markdown-состояние;
- миграции проверяются на `rhizome-test` до стабильного окружения;
- PostgreSQL использует сохраняемый volume и проверяемое резервное копирование
  до production hardening.

### 9.3. Наблюдаемость

- process health отделен от database/integration health;
- ошибки синхронизации содержат correlation/context без утечки секретов;
- аудит связывает бизнес-действие с пользователем, ролью, слоем, proposal и Git
  revision.

### 9.4. Рост единой общей ризомы

- Graph API возвращает ограниченный подграф, а не всю базу по умолчанию;
- notes, links, revisions и proposals имеют подходящие PostgreSQL indexes;
- re-index поддерживает affected-set/incremental path и проверяемый full rebuild;
- proposal/history lists используют pagination и retention/archival policy;
- опубликованная shared revision переключается только после полной готовности;
- новые инфраструктурные компоненты добавляются только по измеренным данным;
- нагрузочные baseline фиксируются на Stage 5, 8 и 9.

## 10. За пределами MVP без отдельного решения

- Telegram, Google/GitHub OAuth и другие внешние identity providers;
- Neo4j;
- Elasticsearch;
- Redis, Celery, RabbitMQ и другие очереди/брокеры;
- S3/MinIO как обязательная инфраструктура;
- собственный Git-сервер или собственный merge-движок;
- Gitea/GitLab;
- Kubernetes;
- полноценный собственный UI ручного three-way merge;
- real-time collaborative text editing;
- хранение или merge канонического `graph.json`;
- редактор GraphNotes «как Obsidian» (preview, autocomplete `[[ ]]`, backlinks,
  локальный граф как замена vault);
- канонические тела заметок в PostgreSQL и кнопки «скопировать заметки в общую»
  в обход Differ и очереди editor’ов;
- запись GraphNotes в personal git как основной способ «взять себе» общую
  ризому (снято ADR-009; исторический Stage 4).

## 11. Актуальная стадийность

Точные границы, ветки и Definition of Done стадий определяются
`docs/context/MASTER_CONTEXT.md`, `docs/context/STAGE_STATUS.md` и активным
`docs/stages/STAGE<N>.md`.

Каноническая последовательность:

1. Stage 0 - Infrastructure;
2. Stage 1 - Project Bootstrap;
3. Stage 2 - Password Authentication;
4. Stage 3 - GitHub Integration (shared repo + connect personal git);
5. Stage 4 - Take from shared / ZIP fallback (исторически DONE; продуктовый
   путь «взять в git» снят ADR-009);
6. Stage 5 - Graph Engine;
7. Stage 6 - Shared graph + personal overlay;
8. Stage 7 - Differ, ZIP download, editor proposal queue / merge / rollback;
9. Stage 8 - Graph Diff (structural view of Differ/proposal);
10. Stage 9 - Production Hardening / CI/CD.

План веток из PDF версии 1.2 считается историческим и не заменяет этот roadmap.

## 12. Открытые продуктовые вопросы

Следующие идеи обсуждаются, но не считаются принятыми требованиями до явного
решения:

1. Минимальный provenance на узле/ребре (автор, слой, revision) в первой волне
   графа.
2. Цвета состояний shared / personal / added / removed / unresolved / proposed.
3. Differ — одностороннее сравнение personal → published shared; предложение
   создаётся из выбранных отличий, не из всего vault. «Взять себе» в MVP —
   ZIP опубликованной общей ризомы, не запись GraphNotes в personal git.
   Кладка ZIP в личный git из GraphNotes — вне текущего MVP.
   (Закрыто ADR-009, 2026-08-19.)
4. Personal remote — отдельный GitHub repository (не fork общей). Первый
   тестовый binding: GraphNotes user `efimov` → `vgdnet/guide_psy`; общая
   ризома → `vgdnet/rhizome`.
5. Редактирование непосредственно через граф — вне MVP, пока нет ADR.
6. Совместное редактирование текста в реальном времени — вне MVP.
7. Отдельный локальный граф текущей заметки сознательно не делается (часть
   «как Obsidian»).

Ответ, который меняет продуктовую модель, security boundary, источник истины
или внешний контракт, оформляется ADR.

## 13. Управление глобальными изменениями

### 13.1. Что требует ADR

ADR обязателен, если решение меняет хотя бы одно из следующего:

- источник истины или модель хранения;
- личный/общественный ownership и merge workflow;
- роли, security boundary или модель доступа;
- ключевую внешнюю систему;
- канонический технологический компонент;
- лицензию;
- topology окружений и promotion gate;
- совместимость публичного API или данных;
- границы MVP настолько, что меняется roadmap или Definition of Done нескольких
  стадий.

### 13.2. Что не требует ADR

Обычно ADR не нужен для локального исправления, внутреннего рефакторинга,
конкретной схемы endpoint внутри одной стадии, UI-детали без изменения
продуктовой семантики или замены библиотеки на совместимую реализацию.

### 13.3. Процесс принятия

```text
вопрос / спор
  -> варианты и последствия
      -> явное решение владельца проекта
          -> ADR со статусом Accepted
              -> обновление PRODUCT_SPEC / MASTER_CONTEXT
                  -> обновление затронутых Stage-документов
```

Непринятое предложение не должно молча попадать в код как новая архитектура.

## 14. Реестр принятых глобальных решений

| ADR | Решение | Влияние на ТЗ |
| --- | --- | --- |
| ADR-001 | Markdown - источник истины | Граф только производный; merge Markdown |
| ADR-002 | Login/password в MVP | Telegram перенесен в future scope |
| ADR-003 | GitHub как Git-движок знаний | Не строим собственный Git/merge engine |
| ADR-004 | Local-first development | Историческая база environment workflow; частично заменена ADR-006 |
| ADR-005 | AGPL-3.0 | Каноническая open-source лицензия проекта |
| ADR-006 | GitHub delivery и read-only production | `nord -> GitHub -> rhizome-test -> rhizome`; без push credentials на production host |
| ADR-007 | Single shared rhizome and global RBAC | Ровно одна общая ризома, одна личная на пользователя, глобальные `user/editor/admin`; multi-workspace исключён |
| ADR-008 | Authoring in Git/Obsidian; GraphNotes as shared layer | Личная ризома = git пользователя; публичное чтение общей; нет in-app Obsidian и нет тел заметок в PostgreSQL |
