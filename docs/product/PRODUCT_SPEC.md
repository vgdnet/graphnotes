# GraphNotes - каноническое техническое задание продукта

Статус: CANONICAL / LIVING DOCUMENT
Версия: 1.0
Обновлено: 2026-08-17

## 1. Назначение документа

Этот документ фиксирует согласованное продуктовое техническое задание
GraphNotes: назначение продукта, пользовательские роли, функциональные
требования, границы MVP и критерии приемки.

Документ создан на основе PDF `GraphNotes_TZ_GitHub_Password_MVP_RU.pdf`, версия
1.2 от 2026-08-15. Более новые принятые решения из ADR и канонического контекста
репозитория имеют приоритет над положениями исходного PDF.

Документы имеют разные зоны ответственности:

- `docs/product/PRODUCT_SPEC.md` - что и для кого должен делать продукт;
- `docs/context/MASTER_CONTEXT.md` - текущая каноническая архитектура;
- `docs/decisions/ADR-*.md` - почему принято глобальное решение и каковы его
  последствия;
- `docs/context/STAGE_STATUS.md` - фактическое состояние реализации;
- `docs/stages/STAGE<N>.md` - исполнимое задание конкретной стадии.

ТЗ не является журналом переписки. Обсуждаемое глобальное изменение становится
каноническим только после явного решения: создается или обновляется ADR, затем
синхронно обновляются затронутые разделы ТЗ и `MASTER_CONTEXT.md`.

## 2. Видение продукта

GraphNotes - многопользовательская Markdown-среда для личных и общественных
графов знаний (ризом).

Пользователь развивает личную версию базы знаний, видит производный граф связей,
сравнивает свои изменения с общественной ризомой и предлагает выбранные
изменения в общее пространство. Reviewer рассматривает предложение, видит
текстовые и графовые последствия и принимает либо отклоняет его.

Ценность продукта состоит не в повторении GitHub или Obsidian, а в визуальном и
управляемом понимании того, как изменения Markdown меняют общую структуру
знания.

## 3. Неподвижные продуктовые принципы

### 3.1. Markdown - источник истины

Каноническое знание хранится в Markdown. Узлы, связи, теги, поисковый индекс и
визуальный граф являются производными данными.

```text
Markdown в Git
  -> parser
      -> PostgreSQL index
          -> Graph API
              -> Web UI
```

Запрещено вводить параллельный канонический `graph.json`. Слиянию и
версионированию подлежит Markdown; после изменения Git-состояния граф
переиндексируется.

### 3.2. Личный и общественный слои

- личный слой содержит изменения конкретного пользователя;
- общественный слой содержит утвержденное знание рабочего пространства;
- личный граф - это проекция личного Markdown-состояния, а не отдельный файл;
- общественный граф - проекция утвержденного Markdown-состояния;
- сравнение слоев строится из различий Markdown и производных узлов/связей.

### 3.3. GitHub скрыт за продуктовым UX

GitHub используется как внешний Git-движок для репозиториев, веток, коммитов,
истории, diff, Pull Request и merge. Обычный пользователь работает с понятиями
«личная база», «общественная ризома», «предложить изменения» и «принять
изменения», а не с branch, SHA и Pull Request.

### 3.4. Граф не является границей безопасности

Разделение веток или визуальных слоев само по себе не обеспечивает изоляцию.
Права проверяются backend на основании внутреннего UUID пользователя, роли и
членства в рабочем пространстве. Пользователям не выдается прямой доступ к
GitHub-репозиториям знаний в обход GraphNotes.

## 4. Термины

| Термин | Определение |
| --- | --- |
| Заметка | Markdown-файл и его индексированное представление |
| Узел | Производное представление заметки или unresolved-ссылки в графе |
| Связь | Производное направленное отношение между заметками из Markdown-ссылки |
| Рабочее пространство | Контекст пользователей, общественного знания, Git-ресурсов и прав |
| Личная база | Пользовательское Markdown-состояние и его производный граф |
| Общественная ризома | Утвержденное Markdown-состояние пространства и его производный граф |
| Предложение | Набор личных изменений, предложенный для общественного слоя |
| Graph diff | Добавленные, удаленные или измененные узлы и связи между двумя Git-состояниями |
| Unresolved link | Ссылка на заметку, которой еще нет в выбранном состоянии |

## 5. Пользовательские группы и права

GraphNotes использует не одну иерархическую роль, а суммируемые группы прав.
`member` является базовой workspace-группой. `editor` и `reviewer` назначаются
независимо и могут совмещаться. `admin` является системной группой с полным
доступом. Backend проверяет конкретное capability и workspace scope.

### 5.1. Member

- регистрируется и входит по логину/паролю;
- работает только в доступных ему пространствах;
- читает доступную общественную ризому;
- импортирует и редактирует Markdown только в личном слое;
- видит личный и доступный общественный граф;
- сравнивает личные изменения с общественным слоем;
- создаёт предложение изменений.

### 5.2. Editor

- имеет права `member` в назначенном workspace;
- напрямую создаёт и редактирует Markdown общей ризомы;
- каждое изменение общей ризомы фиксируется Git commit, audit event и
  переиндексацией;
- право редактирования не даёт автоматически право принимать предложения.

### 5.3. Reviewer

- видит очередь предложений назначенного workspace;
- видит автора, текстовый diff и preview изменения графа;
- принимает, отклоняет или запрашивает доработку;
- не может принять собственное предложение;
- право review не даёт автоматически право напрямую редактировать общую ризому.

### 5.4. Admin

- является системным суперпользователем и имеет все capabilities во всех
  workspaces;
- управляет пользователями, группами прав и системными настройками;
- управляет привязкой GitHub-ресурсов и пересборкой индекса;
- видит системный аудит;
- может редактировать личную и общую ризому и принимать предложения;
- все привилегированные действия, включая override, обязательно аудируются;
- не может обходить Markdown/Git source of truth и правила согласованности.

Пользователь может одновременно иметь `editor` и `reviewer` в одном workspace.
Назначение в одном workspace не переносится в другое. Только `admin` назначает
и отзывает привилегированные группы в MVP.

## 6. Функциональные требования MVP

### 6.1. Аутентификация

- GraphNotes использует собственную регистрацию и login/password;
- внутренний идентификатор пользователя - UUID;
- открытый пароль не хранится и не логируется;
- хранится только стойкий `password_hash`;
- поддерживаются login, logout, текущий пользователь и безопасный механизм
  продолжения сессии;
- пользователь может быть заблокирован без удаления данных;
- регистрация не позволяет самостоятельно получить `editor`, `reviewer` или
  `admin`;
- Telegram остается будущим optional identity provider, привязанным к
  существующему UUID, и не входит в MVP.

Минимальная модель пользователя:

| Поле | Назначение |
| --- | --- |
| `id` | Внутренний UUID |
| `username` | Уникальный логин |
| `password_hash` | Стойкий хеш пароля |
| `email` | Nullable-резерв для восстановления/уведомлений |
| `display_name` | Имя в интерфейсе |
| `is_system_admin` или эквивалентная system-group assignment | Системная группа `admin`; workspace-группы хранятся отдельно |
| `is_active` | Состояние блокировки |
| `created_at`, `updated_at` | Служебные даты |

Workspace membership и назначения `editor`/`reviewer` хранятся отдельно от
учётной записи пользователя. Точная схема определяется Stage 3, но не должна
возвращаться к единственному взаимоисключающему enum ролей.

### 6.2. Рабочие пространства и GitHub

- GraphNotes связывает рабочее пространство с GitHub-ресурсом знаний;
- утвержденное состояние соответствует основной ветке пространства;
- личные изменения представлены пользовательским Git-состоянием;
- backend выполняет GitHub-операции от имени приложения;
- commit SHA сохраняется в индексе для проверки согласованности;
- недоступность или rate limit GitHub отражается явным статусом синхронизации;
- visibility и модель изоляции knowledge-репозиториев должны быть подтверждены
  отдельным ADR до реализации Stage 3; публичность репозитория исходного кода
  GraphNotes не означает публичность пользовательских баз знаний.

### 6.3. Импорт и обработка Markdown

- импорт одного `.md` файла;
- пакетный импорт Markdown из ZIP;
- проверка расширений, размера, числа файлов и безопасности путей;
- нормализация Git-путей без directory traversal;
- извлечение заголовка, wikilinks, Markdown-ссылок, alias, тегов и YAML
  frontmatter в объеме, определенном Stage 4;
- сохранение unresolved links;
- фиксация импортированных изменений в пользовательском Git-состоянии;
- создание отчета об успешных и отклоненных файлах.

### 6.4. Индекс знаний

PostgreSQL хранит производный индекс и состояние приложения, включая как
минимум:

| Сущность | Минимальное назначение |
| --- | --- |
| `note_index` | Заметка, workspace, владелец/слой, Git-путь, title, slug, content hash, commit SHA |
| `note_links` | Источник, цель или unresolved title, тип и исходное представление ссылки |
| `tags`, `note_tags` | Нормализованные теги и отношения |
| `sync_jobs` | Репозиторий/ветка/revision, статус, ошибка и время синхронизации |
| `proposals` | Автор, workspace, исходное/целевое состояние, статус и решение |

PostgreSQL не становится вторым источником Markdown. Индекс должен быть
восстановим из канонического Git-состояния.

### 6.5. Graph API и визуализация

MVP должен предоставлять:

- личный граф;
- общественный граф;
- graph diff предложения;
- узлы заметок и направленные связи;
- открытие заметки из узла;
- базовые фильтры;
- различимое отображение unresolved links;
- обработку пустого, изолированного и частично разрешенного графа;
- получение ограниченного подграфа без обязательной передачи всей базы при
  больших объемах.

Визуализация реализуется на React + TypeScript с Cytoscape.js, если новый ADR не
изменит это решение.

### 6.6. Публикация в общественную ризому

```text
личное Markdown-состояние
  -> предложение
      -> GitHub diff / Pull Request
          -> review редактора
              -> merge утвержденного Markdown
                  -> webhook/reconciliation
                      -> переиндексация общественной ризомы
```

Пользователь должен иметь возможность:

- выбрать изменения для публикации;
- создать предложение;
- увидеть состояние предложения;
- увидеть текстовые и графовые последствия в доступном для стадии объеме.

Reviewer должен иметь возможность:

- увидеть список и автора предложений;
- просмотреть текстовый diff или безопасно перейти к нему в GitHub;
- увидеть добавленные/удаленные узлы и связи;
- принять предложение через GitHub merge;
- отклонить предложение без merge;
- увидеть статус конфликта, не скрывая необходимость ручного разрешения.

После merge общественный индекс обязан соответствовать merged commit SHA.

### 6.7. Аудит и восстановление

- значимые действия пользователя и редактора журналируются;
- GitHub сохраняет техническую историю commit/PR;
- GraphNotes хранит бизнес-события и связь с Git revision;
- должна существовать ручная безопасная пересборка производного индекса;
- повторная обработка webhook не должна создавать дублирующее состояние.

## 7. Черновой контракт API MVP

Точные схемы, коды ошибок и авторизация определяются стадиями. Следующие маршруты
фиксируют продуктовую поверхность, но не требуют преждевременной реализации.

```text
POST /api/auth/register
POST /api/auth/login
POST /api/auth/refresh
POST /api/auth/logout
GET  /api/users/me

GET  /api/workspaces
GET  /api/workspaces/{id}/repo/status

POST /api/workspaces/{id}/upload-md
GET  /api/workspaces/{id}/notes
GET  /api/notes/{id}

GET  /api/workspaces/{id}/graph/personal
GET  /api/workspaces/{id}/graph/shared
GET  /api/workspaces/{id}/graph/diff?proposal_id=...

POST /api/workspaces/{id}/proposals
GET  /api/proposals
GET  /api/proposals/{id}
POST /api/proposals/{id}/approve
POST /api/proposals/{id}/reject

POST /api/webhooks/github
```

Изменение API-контракта в ходе проектирования стадии допустимо без отдельного
ADR, если не меняет продуктовую модель или внешние интеграционные обязательства.

## 8. Критерии приемки MVP

MVP считается функционально готовым, когда:

- пользователь регистрируется и входит по логину/паролю;
- открытый пароль нигде не хранится;
- пользователь имеет изолированное личное Markdown-состояние;
- `.md`/ZIP импортируется с валидацией и фиксируется в Git;
- система индексирует wikilinks, Markdown-ссылки, теги и unresolved links;
- индекс связан с конкретной Git revision;
- пользователь видит личный граф;
- пользователь видит доступную общественную ризому;
- пользователь создает предложение изменений;
- reviewer видит текстовый diff и graph diff/preview;
- reviewer принимает или отклоняет предложение;
- после merge общественная ризома переиндексируется до merged revision;
- PostgreSQL-индекс может быть восстановлен из Markdown/Git;
- ни один graph-файл не используется как параллельный источник истины;
- применимые security, migration, backup и deployment проверки текущих стадий
  выполнены на `rhizome-test` до продвижения на `rhizome`.

## 9. Нефункциональные требования

### 9.1. Безопасность

- все операции проверяют аутентификацию, capability и workspace scope;
- секреты не коммитятся и не возвращаются в API/логи;
- загрузки ограничены и защищены от traversal и архивных бомб;
- webhook GitHub проверяется криптографически;
- GitHub credentials имеют минимально необходимые права;
- deployment Git-доступ на `rhizome` только read-only без push-capable
  credentials;
- backend и PostgreSQL не публикуются в LAN/DMZ без отдельного решения.

### 9.2. Надежность и согласованность

- операции синхронизации имеют наблюдаемый статус и понятную ошибку;
- webhook и фоновые reconciliation-операции идемпотентны;
- при расхождении Git и индекса побеждает каноническое Git/Markdown-состояние;
- миграции проверяются на `rhizome-test` до стабильного окружения;
- PostgreSQL использует сохраняемый volume и проверяемое резервное копирование
  до production hardening.

### 9.3. Наблюдаемость

- process health отделен от database/integration health;
- ошибки синхронизации содержат correlation/context без утечки секретов;
- аудит связывает бизнес-действие с пользователем, workspace и Git revision.

## 10. За пределами MVP без отдельного решения

- Telegram, Google/GitHub OAuth и другие внешние identity providers;
- Neo4j;
- Elasticsearch;
- Redis, Celery, RabbitMQ и другие очереди/брокеры;
- S3/MinIO как обязательная инфраструктура;
- собственный Git-сервер или собственный merge-движок;
- Gitea/GitLab;
- Kubernetes;
- полноценный собственный UI ручного three-way merge;
- real-time collaborative text editing;
- хранение или merge канонического `graph.json`.

## 11. Актуальная стадийность

Точные границы, ветки и Definition of Done стадий определяются
`docs/context/MASTER_CONTEXT.md`, `docs/context/STAGE_STATUS.md` и активным
`docs/stages/STAGE<N>.md`.

Каноническая последовательность:

1. Stage 0 - Infrastructure;
2. Stage 1 - Project Bootstrap;
3. Stage 2 - Password Authentication;
4. Stage 3 - GitHub Integration;
5. Stage 4 - Markdown Import;
6. Stage 5 - Graph Engine;
7. Stage 6 - Personal Graph;
8. Stage 7 - Publish / Pull Request / Merge;
9. Stage 8 - Graph Diff;
10. Stage 9 - Production Hardening / CI/CD.

План веток из PDF версии 1.2 считается историческим и не заменяет этот roadmap.

## 12. Открытые продуктовые вопросы

Следующие идеи обсуждаются, но не считаются принятыми требованиями до явного
решения:

1. Нужен ли отдельный локальный граф текущей заметки и какая глубина обхода
   требуется в MVP.
2. Разрешено ли редактирование непосредственно через граф. Если да, любое
   действие с узлом/связью обязано преобразовываться в изменение Markdown, а не
   создавать второй источник истины.
3. Какие цвета и состояния используются для shared, personal, added, removed,
   modified, unresolved, proposed и conflicting элементов.
4. Какой provenance показывается для узла и связи: автор, слой, branch/revision,
   proposal и состояние публикации.
5. Должен ли пользователь публиковать только выбранные изменения или весь
   актуальный личный diff.
6. Как изолируются knowledge-репозитории разных workspace в GitHub.
7. Нужна ли совместная работа в реальном времени после MVP и на каком уровне:
   presence, уведомления или одновременное редактирование текста.

Ответ, который меняет продуктовую модель, security boundary, источник истины
или внешний контракт, оформляется ADR.

## 13. Управление глобальными изменениями

### 13.1. Что требует ADR

ADR обязателен, если решение меняет хотя бы одно из следующего:

- источник истины или модель хранения;
- личный/общественный ownership и merge workflow;
- группы прав, capabilities, security boundary или модель доступа;
- ключевую внешнюю систему;
- канонический технологический компонент;
- лицензию;
- topology окружений и promotion gate;
- совместимость публичного API или данных;
- границы MVP настолько, что меняется roadmap или Definition of Done нескольких
  стадий.

### 13.2. Что не требует ADR

Обычно ADR не нужен для локального исправления, внутреннего рефакторинга,
конкретной схемы endpoint внутри одной стадии, UI-детали без изменения
продуктовой семантики или замены библиотеки на совместимую реализацию.

### 13.3. Процесс принятия

```text
вопрос / спор
  -> варианты и последствия
      -> явное решение владельца проекта
          -> ADR со статусом Accepted
              -> обновление PRODUCT_SPEC / MASTER_CONTEXT
                  -> обновление затронутых Stage-документов
```

Непринятое предложение не должно молча попадать в код как новая архитектура.

## 14. Реестр принятых глобальных решений
